глава 1 · определение что такое CQRS за одну минуту

Сначала одно слово, без которого дальше не понять ничего. Модель — это форма, в которой код держит данные: класс с полями и методами. Например, класс Order с полями «номер», «товары», «сумма», «статус» и методом «оформить».

CQRS (Command Query Responsibility Segregation, «разделение команд и запросов») — это правило: код, который меняет данные, и код, который показывает данные, пишутся отдельно. У каждого своя модель: у записи — класс с правилами, у чтения — плоский класс ровно под экран.

Звучит абстрактно, поэтому сразу посмотрим на живом примере. Анна делает в магазине две вещи. Выберите, как написан код, и нажмите на действие Анны. Сравните цифры внизу.

глава 2 · две половины команда или запрос

В первой главе мы разделили код Анны на две половины. У них есть имена, и от них CQRS получил свои буквы: Command — команда, Query — запрос.

Всё, что пользователь делает в системе, бывает двух видов. Отличить их можно одним вопросом: изменится ли что-нибудь после этого действия?

✍️ Команда: «сделай»

Меняет данные, поэтому сначала проверяет правила. Отвечает коротко: «готово» или «нельзя, потому что…». Если повторить команду, результат может получиться другим.

👁 Запрос: «покажи»

Ничего не меняет и отдаёт готовый вид под экран. Можно повторять сколько угодно раз, мир от этого не изменится.

Это и есть CQRS целиком. Команды идут через повара с правилами, запросы идут к витрине с готовыми ответами. В коде это значит: для команд доменные объекты, для запросов отдельные запросы сразу в DTO под экран. Одна база, никаких очередей.

Сначала расшифруем страшные буквы

  C Q R S

  команды   запросы    ответственность   разделение

  дословно: «разделяем ответственность
            за команды и за запросы»

  по-человечески: ЗАПИСЬ И ЧТЕНИЕ — РАЗНЫЕ ЗАДАЧИ,

                  не обязательно
И это вся идея целиком. Никакой второй базы, никаких событий, никаких очередей в определении нет. Всё это — возможные способы применения, а не сам приём.

Житейски: пекарня

На кухне важны рецепт, граммы, порядок действий, температура. Ошибся — выбросил партию.

На витрине важно другое: красиво выложить, быстро найти, быстро отдать. Покупателю не нужно знать про граммы и температуру — ему нужны название, цена и картинка.

Это одна и та же булочка, но два совершенно разных взгляда на неё. Никому не приходит в голову заставлять продавца отпускать товар прямо из тестомеса — а в коде мы делаем именно это, когда одну и ту же модель используем и для записи, и для показа.

глава 7 · уровни три уровня CQRS — выбирайте минимальный

1. Разные модели в коде

Одна база. Запись идёт через доменные объекты с правилами, чтение — отдельными запросами сразу в DTO, мимо сущностей. Почти всегда полезно и почти бесплатно. С этого стоит начинать всем.

2. Отдельная схема для чтения

Денормализованные таблицы или материализованные представления в той же базе, обновляемые при изменениях. Появляется отставание, зато тяжёлые экраны отдаются одним запросом без единого JOIN.

3. Отдельное хранилище для чтения

Витрина в другой БД: Elasticsearch для поиска, Redis для горячих счётчиков, колоночная база для аналитики. Наполняется событиями. Дорого: отставание, перестроение, согласованность, отдельная эксплуатация.

Проще говоря. Кладовщик и продавец смотрят на один и тот же товар по-разному: одному нужен ряд и полка, другому — цена и картинка. Не надо делать одну таблицу на двоих. CQRS — это «пусть у каждого будет свой удобный вид», и начинается он не с баз, а просто с двух разных запросов в коде.
Частая ошибка: прыгать сразу на третий уровень, потому что «CQRS — это когда две базы». В девяти случаях из десяти хватает первого, и он не стоит ничего: просто перестаньте тянуть сущности ORM в экраны и напишите отдельные запросы под конкретные представления.

глава 12 · а это другое event sourcing: зачем хранить историю вместо остатка

Сразу разведём два понятия, их постоянно путают. CQRS — про то, что чтение и запись разделены. Event sourcing — про то, что именно лежит в хранилище. Это разные приёмы, и они прекрасно живут по отдельности: CQRS без event sourcing встречается в сто раз чаще.

Житейски: банковская выписка

Представьте, что банк хранил бы только остаток на счету: 12 400 ₽. И всё. Никакой истории.

Вы приходите и говорите: «у меня пропали три тысячи». Что ответит банк? Ничего. У него нет данных, откуда взялось число 12 400. Он не может ни доказать свою правоту, ни найти ошибку, ни отменить одну операцию.

Поэтому банк хранит наоборот: список операций. А остаток — это просто их сумма, которую можно пересчитать в любой момент. Event sourcing — это ровно тот же выбор, только в коде.

Что это даёт — по шагам

глава 12 · продолжение хранить не состояние, а историю

Обычная система хранит текущее состояние: «баланс 1200». Event sourcing хранит все события: «начислено 1000», «начислено 500», «списано 300» — а состояние вычисляется их проигрыванием. Журнал событий неизменяем: исправление — это новое компенсирующее событие, а не UPDATE.

Обычное хранение

accounts
┌────────┬─────────┐
│ id     │ balance │
├────────┼─────────┤
│ acc-1  │   1200  │   ← как пришли к 1200,
└────────┴─────────┘      неизвестно

Event sourcing

events (append-only)
┌───┬────────┬──────────────┬──────┐
│ # │ acc    │ type         │ amt  │
├───┼────────┼──────────────┼──────┤
│ 1 │ acc-1  │ Deposited    │ 1000 │
│ 2 │ acc-1  │ Deposited    │  500 │
│ 3 │ acc-1  │ Withdrawn    │  300 │
└───┴────────┴──────────────┴──────┘
balance = 1000 + 500 − 300 = 1200
плюс ответ на вопрос «почему»

Что обязательно прилагается

  • Снимки (snapshots). Проигрывать 400 тысяч событий на каждое чтение нельзя — периодически сохраняется состояние на момент N, дальше проигрывается хвост.
  • Проекции. Запросы «покажи всех клиентов с балансом больше 1000» по журналу событий невозможны — нужны построенные из него модели чтения. Поэтому ES почти всегда идёт в паре с CQRS.
  • Версионирование событий. События живут вечно, а формат меняется. Нужен план: апгрейд при чтении, версии типов, никогда не менять старые записи.
  • Ответ про персональные данные. Журнал неизменяем, а закон требует удалять. Обычное решение — крипто-стирание: персональные данные в событии зашифрованы, удаляется ключ.
Когда event sourcing точно не нужен: обычный CRUD, справочники, каталоги, административные панели — то есть подавляющее большинство кода. ES оправдан там, где история сама по себе ценна: финансовые операции, аудит по требованию регулятора, сложные доменные процессы с разбором «почему получилось так». Применение ES ко всей системе — надёжный способ утроить сложность ради выгоды в 5 % кода.
