Сентябрь. У «Ботинка» есть сервис заказов. До сих пор его вызывал только сайт. Сайт и сервис делает одна команда, и выкатываются они вместе: поменяли поле — в тот же вечер поправили сайт. Отсюда главное правило раздела: вы не решаете, когда потребители обновят свой код. Значит, каждое изменение контракта должно либо не ломать старых потребителей, либо выходить новой версией с долгим сроком жизни старой. Подробно — в главе 10.

Закон Хайрама. Инженер Google Хайрам Райт заметил: когда у API много пользователей, любое наблюдаемое поведение кто-то начинает использовать — даже то, чего вы не обещали. Порядок заказов в списке, текст ошибки, время ответа. Поэтому в контракте полезно прямо писать не только что гарантировано, но и что не гарантировано: «порядок элементов items не определён».

Что сначала: код или контракт?

Сначала код (code-first)

Борис пишет сервис, описание API генерируется из кода. Быстро, когда потребитель один и в той же команде. Минус: контракт получается «каким вышел», а потребители ждут готового кода, чтобы узнать, что им пришлют.

Сначала контракт (contract-first, design-first)

Олег пишет файл контракта (OpenAPI, глава 11) и согласует его с потребителями до кода. Потом все работают параллельно: мобильщики — на мок-сервере, Борис — над сервером, «Стеллаж» — над интеграцией.

API как продукт (API-first)

Это про отношение, а не про порядок работ. У API есть свои пользователи, документация, журнал изменений, сроки поддержки. Его проектируют как продукт, а не как побочный эффект сервиса.

На практике слова API-first и contract-first часто используют как синонимы. Суть одна: договор появляется раньше реализации и проверяется автоматически. Вот как у Олега идёт работа над API заказов:

«Изменения API заказов публикуются только через ревью файла контракта (OpenAPI). Ломающие изменения — только в новой основной версии. Старая версия поддерживается не менее 6 месяцев после объявления о выводе.»

Типичные ошибки. 1) «API — это то, что сейчас возвращает сервер»: контракта нет, есть код, и любое исправление в коде тихо меняет договор. 2) «Отдадим сущность из базы как есть»: наружу утекают внутренние поля, и каждое изменение таблицы ломает клиентов. Наружу отдают отдельную модель ответа, а не строку таблицы.

глава 2 · ресурсы ресурсы и адреса: о чём говорит API

Олег начинает с простого вопроса: о каких вещах будут разговаривать программы? Заказ, покупатель, товар, корзина, платёж. В REST такие вещи называются ресурсами.

REST (Representational State Transfer) — стиль построения API поверх HTTP, описанный Роем Филдингом в 2000 году. Главная идея: API состоит из ресурсов с адресами, а действия над ними выражаются стандартными методами HTTP.
Ресурс — вещь, о которой говорит API: заказ, товар, корзина. У ресурса есть адрес и представление — то, как он выглядит в ответе (обычно JSON). URI (Uniform Resource Identifier) — адрес ресурса.
библиотечный каталог. У каждой книги есть шифр места на полке. Вы не пишете в формуляре «принеси-мне-книгу-про-кроссовки». Вы называете шифр, а действие — «выдать», «вернуть», «продлить» — выбираете отдельно. Шифр — это URI, действие — метод.
Коллекция — ресурс-список: /orders — все заказы. Элемент — один ресурс из коллекции: /orders/ord-1042 — один заказ.

глава 3 · методы что обещает каждый глагол HTTP

Адрес говорит «о чём», метод — «что сделать». Смысл методов закреплён в стандарте RFC 9110 «HTTP Semantics» (2022). Это важно: на этот смысл полагаются не только ваши клиенты, но и прокси, кеши, шлюзы и браузеры. Если метод врёт о себе, они сделают неправильные выводы.

Безопасный метод (safe) — по замыслу не меняет ничего на сервере. Клиент может вызывать его сколько угодно: это просто чтение.

PUT или PATCH?

PUT — «вот полное новое состояние»

PUT /v1/orders/ord-1042/delivery-address
Content-Type: application/json

{"city": "Москва", "street": "Лесная", "house": "5",
 "flat": "12", "comment": "домофон не работает"}

Всё, чего нет в теле, будет стёрто. Повтор безопасен: второй раз запишется то же самое. Опасность — в устаревшей копии: если кто-то успел поменять ресурс, PUT затрёт его правки (глава 8).

PATCH — «вот что поменять»

PATCH /v1/orders/ord-1042
Content-Type: application/merge-patch+json

{"deliveryDate": "2026-10-04", "comment": null}

Формат JSON Merge Patch (RFC 7396): перечисленные поля заменяются, null означает «удалить поле», остальное не трогается. Есть и JSON Patch (RFC 6902) — список операций: [{"op":"replace","path":"/deliveryDate","value":"2026-10-04"}]. Сам метод PATCH описан в RFC 5789.

GET никогда ничего не меняет. Представьте ссылку GET /orders/ord-1042/cancel в письме Анне. Почтовый сервис проверит ссылку на вирусы, мессенджер построит превью, браузер подгрузит заранее — и каждый из них отменит заказ. Они вправе ходить по GET-ссылкам без спроса: метод обещал, что это безопасно.

Модель зрелости Ричардсона: четыре ступени к REST

Леонард Ричардсон предложил оценивать HTTP API по четырём уровням, а Мартин Фаулер в 2010 году сделал эту схему известной. Посмотрите, как одна и та же операция — «создать заказ и узнать, что с ним можно делать» — выглядит на каждом уровне.

Где жить на практике. Большинство хороших API живут на уровне 2 — и это нормально. Уровень 3 (HATEOAS, Hypermedia As The Engine Of Application State — «гипермедиа как двигатель состояния») встречается редко: клиенты всё равно пишутся под конкретные поля. Но одна его идея очень полезна аналитику: отдавать в ответе список действий, доступных в текущем статусе. Тогда кнопку «Отменить» приложение показывает, только если сервер прислал ссылку на отмену, и правила статусной модели живут в одном месте.

«Отмена заказа: POST /v1/orders/{orderId}/cancellation. Метод не идемпотентен по HTTP. Повтор допускается: если заказ уже отменён, сервер возвращает тот же результат, что и в первый раз (см. „Идемпотентность“).»

глава 4 · ответы коды ответов и заголовки: язык, который понимают все

Код ответа (status code) — трёхзначное число в первой строке ответа HTTP. Первая цифра — класс: 2xx — успех, 3xx — перенаправление, 4xx — ошибка клиента (исправь запрос; повторять его как есть бессмысленно), 5xx — ошибка сервера (можно повторить позже). Есть ещё 1xx — служебные, в проектировании API почти не встречаются.
окошко в МФЦ. «Готово, вот паспорт» — 2xx. «Это в соседнем окне» — 3xx. «Вы неправильно заполнили заявление» — 4xx: приходить с тем же бланком снова бесполезно. «У нас сломался принтер, зайдите через час» — 5xx: приходите с тем же бланком, всё получится.

Коды читают не только люди. Шлюз решает по ним, повторять ли запрос. Кеш — можно ли сохранить ответ. Мониторинг считает долю 5xx и будит дежурного. Поэтому ответ 200 OK с телом {"error": "заказ не найден"} — это ложь всем сразу: шлюз закеширует ошибку, мониторинг покажет «всё отлично», а клиент должен разбирать тело, чтобы понять, успех ли это.

400 или 422 на ошибку проверки? В RFC 9110 код 400 означает «запрос не разобрать как ошибку клиента» (битый JSON, строка вместо числа), а 422 Unprocessable Content — «запрос понятен, но данные нарушают правила» (количество −1). Многие API отдают 400 на всё — это тоже допустимо. Важно одно: одно правило на весь API, записанное в руководстве по стилю.

глава 5 · ошибки ошибки по стандарту: Problem Details

Первая неделя интеграции. Вика, разработчица «Стеллажа», пишет Олегу: «У вас три метода — и три формата ошибок». Метод создания заказа отвечает {"error": "bad request"}. Метод оплаты — {"code": 17, "message": "..."}. А когда сервис лежит, шлюз отдаёт HTML-страницу с надписью «502 Bad Gateway». Правила хорошей ошибки

Честный код

Никаких 200 с ошибкой внутри и никаких 500 на ошибку клиента. Код — первое, что видят шлюзы, мониторинг и логика повторов.

Без внутренностей

Стек вызовов, текст SQL, имена серверов помогают только взломщику. А ещё они становятся частью контракта: кто-то начнёт разбирать текст исключения (закон Хайрама).

Все ошибки полей сразу

Если в заказе пять ошибок, верните все пять в списке errors. Иначе Анна будет исправлять форму пять раз подряд. У каждой ошибки — указатель на поле (pointer в формате JSON Pointer).

Один формат везде

Шлюз, балансировщик и прокси тоже должны отвечать в application/problem+json, а не своей HTML-страницей. Это настройка, её надо заказать явно.

Код ошибки для программ. Часто хочется добавить поле code: "ORDER_ALREADY_SHIPPED". По стандарту эту роль играет type. Дублировать можно, но закрепите, какое поле главное. И помните: список type — часть контракта. Новый вид ошибки совместим, только если клиенты умеют обработать незнакомый type по классу кода (4xx / 5xx).

«Все ошибки возвращаются в формате RFC 9457 (application/problem+json). Ошибки проверки полей — код 422, type = …/validation-error, список errors[] с полями pointer и detail; возвращаются все ошибки запроса сразу.»

Два способа листать

Смещение (offset / limit)

Курсор (cursor / keyset)

WHERE (created_at, id) < ('2026-09-30 19:31', 'ord-1037')
ORDER BY created_at DESC, id DESC
LIMIT 20;

Плата: нельзя прыгнуть на седьмую страницу, общее число страниц неизвестно, сортировать можно только по полям с индексом.

Курсор — непрозрачная строка-закладка, которую сервер выдаёт вместе со страницей. Клиент её не разбирает и не собирает сам, а просто возвращает в следующем запросе. Внутри обычно закодированы значения полей сортировки (так называемый keyset — «набор ключей»).

глава 7 · идемпотентность двойное «Оплатить»

19:40, метро. Анна жмёт «Оплатить 7 980 ₽». Приложение десять секунд крутит колёсико и пишет «Ошибка сети». Анна жмёт ещё раз — и всё проходит. Через минуту приходят две SMS о списании.

Что случилось на самом деле? Первый запрос дошёл, деньги списались, а ответ потерялся в тоннеле. Приложение не может отличить «запрос не дошёл» от «ответ не дошёл»: в обоих случаях оно просто ничего не получило. Основы идемпотентности уже разобраны в разделе . Здесь — как это спроектировать до конца: что хранит сервер, что отвечать в каждом случае и что записать в контракт.

Ключ идемпотентности (заголовок Idempotency-Key) — уникальная строка, которую клиент придумывает на одно намерение («оплатить заказ ord-1042») и повторяет в каждом повторе. По ключу сервер узнаёт повтор и отдаёт сохранённый ответ вместо повторного выполнения.
вы звоните в пиццерию и называете номер заказа, который придумали сами: «заказ 5521, маргарита». Связь оборвалась, вы перезваниваете: «заказ 5521, маргарита». Оператор видит, что 5521 уже готовят, и не заводит вторую пиццу.
Статус стандарта на 2026 год. Заголовок описан в черновике IETF draft-ietf-httpapi-idempotency-key-header (последняя редакция — 07, октябрь 2025). Стандартом RFC он пока не стал, но именно так устроены API крупных платёжных сервисов. Черновик рекомендует: значение — строка (обычно UUID); ключ без тела другого запроса не переиспользуется; срок хранения ключей сервер публикует в документации.

Как сервер обрабатывает ключ — по шагам

CREATE TABLE idempotency_keys (
  client_id    text        NOT NULL,  -- кто прислал: у разных клиентов ключи не пересекаются
  key          text        NOT NULL,  -- значение Idempotency-Key
  fingerprint  char(64)    NOT NULL,  -- SHA-256 от метода, пути и тела запроса
  state        text        NOT NULL,  -- in_progress | completed
  status_code  int,                   -- сохранённый код ответа
  response     jsonb,                 -- сохранённое тело ответа
  expires_at   timestamptz NOT NULL,  -- обычно через 24 часа
  PRIMARY KEY (client_id, key)        -- из двух одновременных вставок пройдёт одна
);

Естественно идемпотентные операции

Лучший ключ идемпотентности — тот, который не нужен. Многие операции можно спроектировать так, что повтор безвреден сам по себе:

«Установи», а не «измени на»

PUT … {"status": "cancelled"} — идемпотентно. «Увеличь количество на 1» — нет: каждый повтор добавит ещё пару кроссовок. Проектируйте команды как «установи значение», где можно.

Естественный уникальный ключ

«Начислить бонусы за заказ ord-1042» — пусть в таблице начислений будет уникальное ограничение на (заказ, причина). Второе начисление просто не вставится.

Клиент задаёт идентификатор

PUT /v1/orders/{uuid-от-клиента} — повтор создаст тот же заказ по тому же адресу, а не второй. Годится, когда клиенту можно доверить выбор идентификатора.

Ключ живёт у клиента

Приложение создаёт ключ, когда Анна начала оплату, и хранит его до окончательного ответа. Новый ключ — только для нового намерения: другая сумма, другая корзина.

Что сохранять, если операция упала. Это решение проекта. Обычно окончательные ответы (2xx и 4xx) сохраняют и отдают при повторе. А при сбое сервера (5xx) ключ освобождают, чтобы повтор мог пройти заново. Запишите выбранное правило в контракт — клиенту важно знать, поможет ли повтор.

«POST /v1/payments требует заголовок Idempotency-Key (UUID). Без заголовка — 400. Повтор с тем же ключом и тем же телом в течение 24 часов возвращает сохранённый ответ первого запроса без повторного списания. Тот же ключ с другим телом — 422 (type = …/idempotency-key-reused). Повтор, пока первый запрос ещё выполняется, — 409; клиент повторяет через время из Retry-After. Ключи привязаны к клиенту (к учётной записи из токена).»

глава 8 · одновременные правки два редактора и одна карточка товара

Утро понедельника. Олег готовит акцию и в админке ставит кроссовкам «Ботинок Air» цену 6 990 вместо 7 980. В ту же минуту Борис правит описание той же карточки: дописывает «водонепроницаемые». Оба открыли карточку в 10:00. Олег сохранил в 10:02, Борис — в 10:03. Через час рассылка обещает покупателям 6 990, а на сайте висит 7 980. Никто не получил ни одной ошибки.

Потерянное обновление (lost update) — одна запись незаметно затирает другую, сделанную параллельно. RFC 9110 прямо называет эту проблему и предлагает против неё условные запросы.
два соавтора правят один документ, скачав его себе. Каждый отправляет обратно свою полную копию. Последний присланный файл и становится документом — правки первого исчезают.
ETag (entity tag, метка сущности) — метка версии представления ресурса. Сервер отдаёт её в заголовке ETag: "v7" и меняет при каждом изменении ресурса.
Оптимистическая блокировка (optimistic locking) — ресурс не запирают на время редактирования. При сохранении клиент говорит: «записывай, только если версия всё ещё "v7"» (If-Match: "v7"). Если версия изменилась — отказ 412 Precondition Failed, клиент перечитывает и повторяет.
правки к договору принимаются «только к редакции № 7». Юрист прислал правки к седьмой, а на столе уже восьмая — правки не вносят вслепую, а просят сверить с новой редакцией.

Живая модель: Олег, Борис и сервер

Как это устроено внутри

-- ETag = номер версии строки
UPDATE products
   SET price = 6990, description = '…', version = version + 1
 WHERE sku = 'BTN-AIR' AND version = 7;   -- версия из If-Match
-- изменена 1 строка  → 200 OK, ETag: "v8"
-- изменено 0 строк   → кто-то успел раньше → 412 Precondition Failed

Почему не «запереть карточку»

Пессимистическая блокировка — «карточку редактирует Олег, остальным нельзя». В вебе она плохо работает: Олег закрыл вкладку и ушёл на обед, а замок висит. Нужны сроки, принудительное снятие, и всё равно кто-то ждёт. Оптимистическая никого не ждёт, а конфликт ловит в момент записи.

Что делать клиенту на 412

Не перезаписывать силой. Перечитать карточку (новый ETag), показать человеку, что изменилось («цену поменял Олег: 7 980 → 6 990»), наложить свои правки на свежую версию и отправить с новым If-Match.

Если If-Match не прислали

Сервер может требовать условный запрос и отвечать 428 Precondition Required (RFC 6585). Так забывчивый клиент не сможет затереть чужие правки.

Сильный и слабый ETag

W/"v8" — слабая метка: «по смыслу то же самое». Годится для кеша. Для If-Match нужна сильная метка без W/ — сравнение там строгое.

Проще говоря. PATCH уменьшает риск (Олег шлёт только цену, Борис — только описание, и они не мешают друг другу). Но если двое меняют одно и то же поле или правка зависит от прочитанного значения («цена минус 10 %»), без If-Match всё равно не обойтись.

«PUT и PATCH /v1/products/{sku} требуют заголовок If-Match со значением ETag из последнего GET. Если карточку изменили после чтения — 412 (Problem Details, type = …/stale-version); интерфейс показывает актуальную версию и различия. Без If-Match — 428.»

глава 9 · тяжёлые операции долго, много, тяжело

Долгие операции: 202 Accepted и ресурс статуса

«Стеллаж» просит отчёт по продажам за год. Сервер собирает его три минуты. Держать HTTP-соединение три минуты нельзя: шлюз оборвёт его через 30–60 секунд и ответит 504, мобильная сеть — ещё раньше. А клиент так и не узнает, собрался отчёт или нет.

Асинхронная операция «запрос — ответ» (asynchronous request-reply) — сервер сразу отвечает 202 Accepted («принято, делаем») и даёт адрес ресурса статуса. Клиент узнаёт результат опросом этого адреса или получает уведомление.
химчистка. Вам не стоять у стойки три дня: дают квитанцию с номером. Можно заходить и спрашивать «готово?», а можно оставить телефон — позвонят сами.
Вебхук (webhook) — обратный вызов по HTTP. Клиент заранее регистрирует свой адрес, и когда событие случилось, ваш сервер сам делает к нему POST.
«не звоните в химчистку каждый час — оставьте номер, мы позвоним». Опрос — это звонить самому. Вебхук — ждать звонка.

Опрос (polling)

Просто, работает через любой файрвол, клиенту не нужен свой сервер. Минус — лишние запросы «ещё нет?». Подсказывайте частоту через Retry-After.

Вебхук

Мгновенно и без лишних запросов. Но у клиента должен быть доступный адрес, а у вас — повторы при неудаче, подпись и журнал доставок.

Вебхук — это ваш API наоборот. Для него действуют те же правила контракта. Подпись: тело подписывают секретом (HMAC), чтобы получатель проверил, что пишете именно вы. Повторы: если получатель не ответил 2xx, доставку повторяют с растущей паузой — значит, получатель должен быть идемпотентным по идентификатору события. Порядок не гарантирован: событие «доставлен» может прийти раньше «отправлен». Быстрый ответ: получатель сразу отвечает 2xx, а обрабатывает потом. Единый формат подписи и заголовков предлагает открытая спецификация Standard Webhooks.

Асинхронные API и AsyncAPI

Когда сервисы обмениваются событиями через брокер (подробно — в разделе ), контракт тоже нужен: какие каналы, какие сообщения, какие поля. Для HTTP его пишут в OpenAPI, а для событий — в AsyncAPI.

AsyncAPI — открытая спецификация для описания асинхронных API: каналы (темы брокера, WebSocket), операции «отправляю» и «получаю», сообщения со схемами. Версия 3.0 вышла в декабре 2023 года, 3.1 — в январе 2026 года (без ломающих изменений). Вебхуки, которые отправляет HTTP-сервис, можно описать и в OpenAPI 3.1 — там для этого есть раздел webhooks.

Всё или ничего?

Главный вопрос пакета. Атомарный пакет: одна ошибка — откат всего, ответ 422 с номером проблемного элемента. Частичный: каждый элемент сам по себе, ответ со статусом по каждому. Выбор записывают в контракт.

Код ответа

При частичном успехе чаще отвечают 200 с результатами по элементам. Некоторые API используют 207 Multi-Status — код из WebDAV. Клиент повторяет только неуспешные элементы.

Пределы

Максимум элементов в пакете (например, 500) и максимальный размер тела. Пакет на 100 000 элементов — это снова «долгая операция», и ему нужен 202.

Частичные ответы. Это ещё и выбор полей (?fields=, глава 6), и докачка больших файлов по частям: клиент просит Range: bytes=1048576-, сервер отвечает 206 Partial Content. Оборвалась загрузка на 80 % — докачиваем оставшиеся 20 %.

Загрузка файлов: подписанная ссылка

«Стеллаж» загружает фото товаров по 20 МБ. Если гнать их через API-сервер, он держит в памяти мегабайты, соединения висят долго, а трафик идёт дважды: к API и от API в хранилище. Кодировать файл в JSON через base64 — ещё хуже: плюс треть к размеру.

Подписанная ссылка (presigned URL) — временный адрес в хранилище файлов, в который уже «вшито» разрешение на одно действие (например, загрузить один файл) до указанного времени. API выдаёт ссылку, а сам файл идёт прямо в хранилище.
разовый пропуск на склад: на одну машину и на один час. Охрана пускает по пропуску, не звоня начальнику. Час прошёл — пропуск недействителен.
Другие варианты. Маленькие файлы (аватар до 1 МБ) проще передать в самом запросе как multipart/form-data. Для очень больших файлов с докачкой после обрыва есть открытый протокол tus. глава 10 · главный интерактив сломает ли клиента?

Борис хочет переименовать total в totalAmount — «так понятнее». Олег просит подождать: «Давай сначала посмотрим, кто и как это поле читает». Это и есть главный навык раздела — до изменения увидеть, кого оно сломает.

Ломающее изменение (breaking change) — изменение контракта, после которого хотя бы один правильно написанный старый клиент перестаёт работать или начинает работать неверно. Обратная совместимость (backward compatibility) — новая версия сервера работает со старыми клиентами без их доработки.
Толерантный читатель (tolerant reader, термин Мартина Фаулера) — клиент, который читает только нужные ему поля, пропускает незнакомые и не падает на неизвестном значении перечисления. Старый принцип из сетевых стандартов (закон Постела) говорит о том же: «будь строг в том, что отправляешь, и снисходителен к тому, что принимаешь».
кассир, который по квитанции проверяет только номер счёта и сумму. Если на бланке появилась реклама или новая графа, он её просто не читает — и продолжает принимать платежи.

Вывод из эксплуатации: как попрощаться со старым

1
Объявить. Запись в журнале изменений, письмо партнёрам, страница «как перейти». В OpenAPI у операции или поля ставят deprecated: true.Сразу называют дату отключения — иначе «потом удалим» не наступит никогда.
2
Помечать каждый ответ. Заголовок Deprecation (RFC 9745, 2025) — с какой даты ресурс устарел. Заголовок Sunset (RFC 8594, 2019) — после какой даты перестанет отвечать. Ссылка на инструкцию — в заголовке Link.Так о выводе узнают даже те, кто не читает рассылки: их клиенты видят заголовки в каждом ответе.
3
Измерять. По журналам считать, какие клиенты и версии приложения ещё ходят в старое. Писать им лично.Мобильное приложение передаёт свою версию (например, в заголовке User-Agent), поэтому видно, сколько телефонов ещё на 3.2.
4
Выдержать срок. Для публичного API обычно 6–12 месяцев. Для мобильного — пока доля старых версий не упадёт ниже порога, например 2 %; остальным показывают экран «обновите приложение».Некоторые компании перед отключением устраивают «плановые затемнения»: выключают старую версию на час, чтобы проснулись забытые клиенты.
5
Отключить. После даты Sunset старый адрес отвечает 410 Gone («было и убрано навсегда») с Problem Details и ссылкой на инструкцию, а не загадочным 404.
HTTP/1.1 200 OK
Content-Type: application/json
Deprecation: @1790812800
Sunset: Wed, 31 Mar 2027 23:59:59 GMT
Link: <https://developer.botinok.example/migrate-to-v2>; rel="deprecation"; type="text/html"

Обратите внимание на форматы дат — они разные по историческим причинам. Deprecation по RFC 9745 — это «дата структурированного поля»: знак @ и число секунд с 1 января 1970 года по UTC (здесь — 1 октября 2026 года, 00:00 UTC). Sunset по RFC 8594 — обычная HTTP-дата.

«Поле customer.phone устарело с 01.10.2026 и будет удалено из ответа GET /v1/orders/{orderId} 31.03.2027. До этой даты ответы содержат заголовки Deprecation и Sunset. Замена — ресурс /v1/customers/{customerId}/contacts. Ответственный за уведомление партнёров — владелец продукта API.»

Что делают с этим файлом

Генерация кода и документации

Генераторы (например, OpenAPI Generator) создают по файлу клиентские библиотеки и заготовки сервера для десятков языков. Документацию с кнопкой «попробовать» строят Swagger UI, Redoc и похожие инструменты. Документация больше не расходится с кодом: она и есть контракт.

Линтинг: Spectral

Линтер проверяет файл на правила стиля: у каждой операции есть operationId, пути в нижнем регистре через дефис, ошибки в application/problem+json. Правила лежат в .spectral.yaml и запускаются в сборке. Руководство по стилю API превращается из PDF в автоматическую проверку.

Поиск ломающих изменений

Утилиты сравнения контрактов (например, oasdiff) сравнивают новую версию файла со старой и валят сборку, если нашли ломающее изменение: удалено поле, появилось обязательное поле в запросе, сменился тип.

Мок-сервер

Мок-сервер (например, Prism или WireMock) поднимается прямо по файлу и отвечает примерами из него. Мобильщики и «Стеллаж» начинают интеграцию в первый день, не дожидаясь Бориса.

# .spectral.yaml — правила стиля API «Ботинка»
extends: ["spectral:oas"]          # базовые правила для OpenAPI
rules:
  paths-kebab-case:
    description: Пути — только строчные буквы, цифры и дефис
    given: "$.paths[*]~"            # ~ означает «ключи»: сами пути
    severity: error
    then:
      function: pattern
      functionOptions:
        match: "^(/([a-z0-9-]+|\\{[a-zA-Z]+\\}))+$"

Контрактные тесты: Pact и договоры от потребителя

Контракт, управляемый потребителем (consumer-driven contract) — каждый потребитель сам записывает, какие запросы он шлёт и какие поля ответа ему действительно нужны. Сборка поставщика проверяет себя по всем таким записям. Самый известный инструмент — Pact.
перед ремонтом управляющая компания обходит квартиры и записывает, у кого где стоит стиральная машина и куда подведена вода. Прежде чем менять трубы, бригада сверяется со списком — и не отрезает воду тем, кто в нём есть.
1
Потребитель пишет тест. Мобильное приложение в своих тестах описывает: «шлю GET /v1/orders/ord-1042, жду 200 и поля id, status, total — целое число». Тест гоняется против заглушки Pact.
2
Получается файл-договор (pact). Его публикуют в общий брокер договоров (Pact Broker).
3
Поставщик проверяет себя. Сборка сервиса заказов проигрывает все договоры всех потребителей против настоящего сервера. Борис переименовал total — упал договор мобильного приложения, и сборка красная ещё до выкладки.
4
Перед выкладкой — «можно ли?». Команда can-i-deploy спрашивает брокер: совместима ли эта версия со всеми версиями потребителей, которые сейчас работают в бою.
OpenAPI или Pact? Не «или», а «и». OpenAPI описывает всё, что поставщик обещает. Pact — то, чем потребители реально пользуются. Первое нужно для документации и генерации. Второе точно отвечает на вопрос «кого сломает это изменение».

глава 12 · другие протоколы gRPC и GraphQL: как растут схемы

Внутри «Ботинка» склад и заказы говорят по gRPC, а приложению для витрины сделали GraphQL. Как устроены эти способы связи, рассказано в разделе . Здесь — только эволюция схем: что можно менять и как не сломать соседей.

Protobuf: поле — это номер, а не имя

syntax = "proto3";

message Order {
  string id = 1;
  OrderStatus status = 2;
  int64 total = 3;               // сумма в копейках
  string currency = 4;
  reserved 5;                    // было: string phone = 5; удалено в версии 1.3
  reserved "phone";              // и имя тоже нельзя занять снова
  optional string delivery_date = 6;   // optional: можно отличить «нет» от «пусто»
  repeated Item items = 7;
}

enum OrderStatus {
  ORDER_STATUS_UNSPECIFIED = 0;  // нулевое значение — «не указано»
  ORDER_STATUS_NEW = 1;
  ORDER_STATUS_PAID = 2;
  ORDER_STATUS_SHIPPED = 3;
}

По проводу летят номера

В двоичном формате Protobuf поле опознаётся по номеру, а не по имени. Имя нужно только для кода и для JSON-представления. Поэтому номер существующего поля менять нельзя никогда.

reserved — могила для номера

Удалили поле — зарезервируйте его номер и имя. Если номер 5 занять новым полем string address = 5, старые клиенты прочтут адрес как телефон — и никто не заметит.

Новые поля — безопасно

Добавить поле с новым номером можно: старый код незнакомое поле пропустит. Новый код, получив сообщение от старого, увидит значение по умолчанию.

optional и значения по умолчанию

Обычное поле proto3 не отличает «прислали 0» от «не прислали». Ключевое слово optional (штатно с protobuf 3.15) добавляет признак присутствия. Для перечислений нулевое значение — всегда «не указано»; новое значение у старого клиента окажется нераспознанным числом, и у кода должна быть ветка «иначе».

Проверку ломающих изменений .proto ставят в сборку — например, командой buf breaking, которая сравнивает схему с предыдущей версией.

GraphQL: эволюция без версий

type Order {
  id: ID!
  status: OrderStatus!
  total: Int! @deprecated(reason: "Используйте totalAmount: сумма с копейками и валютой")
  totalAmount: Money!
}

Добавлять — всегда можно

Клиент GraphQL сам перечисляет нужные поля. Новое поле старый клиент просто не запросит — поэтому добавление ничего не ломает.

Удалять — через @deprecated

Поле или значение перечисления помечают @deprecated(reason: …). Инструменты подсвечивают его у разработчиков клиентов, а сервер видит статистику: кто ещё запрашивает старое поле. Когда таких не осталось — удаляют.

Обязательность

Зеркальное правило REST: сделать поле ответа из Int! необязательным Int — ломает (клиент не ждёт null). Сделать аргумент из необязательного обязательным — ломает запросы.

Новое значение enum

Как и в REST: клиенты со строгим перечислением падают. Договаривайтесь заранее, что список может расти, и проверяйте по статистике использования.

Scope (область доступа) — право, записанное в токене: orders:read, orders:write. «Стеллажу» выдают только то, что нужно для его сценария. Не хватает scope — 403.

BOLA (Broken Object Level Authorization — сломанная проверка доступа к объекту) — сервер проверил, что токен настоящий, но не проверил, что этот заказ принадлежит этому пользователю. Первое место в списке OWASP API Security Top 10 (2023).

Лишние поля в запросе

Приложение прислало в PATCH не только адрес, но и "status": "paid" или "price": 1. Если сервер записывает всё подряд — это «массовое присваивание». Принимайте только поля из контракта для этой операции и отдавайте только нужные. В OWASP это пункт API3:2023.

Лимиты и размеры

Квота на клиента (например, «Стеллажу» 50 запросов в секунду), превышение — 429 с Retry-After. Максимальный размер тела — иначе 413 Content Too Large. Максимальный limit в списках. В OWASP это API4:2023 — «неограниченное потребление ресурсов». Механика лимитов — в разделе .

CORS

CORS (Cross-Origin Resource Sharing) — правило браузера: скрипт со страницы одного сайта может читать ответы API другого сайта, только если API разрешил это заголовком Access-Control-Allow-Origin. Для «непростых» запросов браузер сначала шлёт предварительный OPTIONS. CORS защищает пользователей браузера, а не ваш API: серверы и утилиты его не соблюдают. * вместе с передачей cookies браузер не примет.

Скорость: кеш, сжатие, «болтливость»

Кеширование HTTP

Каталог товаров меняется редко: Cache-Control: public, max-age=300 — пять минут его можно брать из кеша браузера, CDN или шлюза. Персональное — private, чувствительное — no-store. Повторная проверка: клиент шлёт If-None-Match: "v8", сервер отвечает 304 Not Modified без тела. Запрос всё равно идёт, но трафика почти нет. Подробно — в разделе .

Сжатие

Клиент говорит Accept-Encoding: gzip, br, сервер отвечает Content-Encoding: br. JSON с его повторяющимися именами полей сжимается в разы — для мобильной сети это заметно.

Болтливый API (chatty) — чтобы нарисовать один экран, клиент делает много мелких запросов. Крупный API (chunky) — один запрос приносит всё, что нужно экрану.
сходить в магазин за продуктами к ужину. Можно пять раз сбегать за каждым продуктом отдельно, а можно один раз по списку. Дорога туда и обратно — это и есть задержка сети. В магазине вы проводите одинаковое время, а вот на дорогу — в пять раз больше.

N+1 на уровне API — частый случай болтливости. Экран списка загрузил 20 заказов (1 запрос), а потом для каждого отдельно запросил позиции (ещё 20). Лечится так: включать связанные данные в ответ (?include=items), читать пачкой (GET /v1/orders?ids=…) или завести BFF.

BFF (Backend for Frontend, «бэкенд для фронтенда») — отдельный серверный слой под конкретного клиента. Мобильный BFF внутри дата-центра сам обходит пять сервисов по быстрой сети и отдаёт экрану один готовый ответ. Подробно — в разделе .
