Сервисы — как люди в большой компании: каждый делает своё дело, но в одиночку заказ не соберёт никто. Им приходится договариваться. Можно позвонить и ждать ответа, можно оставить записку, можно повесить объявление для всех. В этом разделе мы проследим один заказ от нажатия кнопки до письма на почту и увидим, какой способ разговора где нужен и почему.

Словарик: слова, которые будут дальше

    

      Синхронно
Отправитель ждёт ответа и без него не продолжает. Как телефонный звонок.

      Асинхронно
Отправитель отдал сообщение и занимается своими делами. Ответ, если он нужен, придёт потом. Как записка или сообщение в мессенджере.

      Сообщение
Кусок данных, который один сервис передаёт другому: просьба или новость.

      Брокер
Отдельная программа-посредник между сервисами, «почтовое отделение». Принимает сообщения, хранит, раздаёт получателям. Примеры: RabbitMQ, Kafka.

      Очередь
Ящик в брокере, где сообщения ждут своего обработчика по порядку. Как очередь с талончиками в поликлинике.

      Команда
Сообщение «сделай»: у него один адресат, и адресат может отказаться.

      Событие
Сообщение «случилось»: факт в прошедшем времени, без адресата. Кому интересно — тот подписан.

      Подписчик
Сервис, который сам попросил брокер присылать ему события определённого вида.

    

  


  
  

    
глава 4 · правило выбора два вопроса, которые выбирают способ

    
Все аналогии из прошлой главы раскладываются по двум вопросам. Ответьте на них за сервис заказов — и получите подходящий способ. Почти все ошибки в интеграции — это попытка решить задачу из одного угла средствами другого.

    

      

      

    

    

      

        
📞 Ждём ответ, знаем получателя — запрос-ответ

        
«Отложи товар», «сколько у меня денег?». REST, gRPC, GraphQL. Ответ нужен, чтобы продолжить работу.

        
Цена: вы зависите от того, жив ли получатель. Его задержка добавляется к вашей.

      

      

        
✉️ Не ждём, знаем получателя — команда в очередь

        
«Сформируй отчёт», «отправь письмо». Кладём задачу в очередь конкретному обработчику и идём дальше.

        
Цена: результат сразу неизвестен. Нужен способ его узнать: статус, обратный вызов или уведомление.

      

      

        
📢 Не ждём, не знаем получателей — событие

        
«Заказ оформлен». Публикуем факт, кому интересно — тот подписан. Отправитель про подписчиков не знает.

        
Цена: процесс целиком не виден ни в одном месте. Данные у соседей обновляются с задержкой. Повторы сообщений неизбежны, их надо уметь переживать.

      

      

        
❓ Ждём ответ, не знаем получателя — почти всегда ошибка

        
«Спрошу у всех, кто-нибудь да ответит». Встречается как «запрос-ответ через брокер» или рассылка вопроса всем.

        
Почему плохо: вы ждёте самого медленного, а при сбое непонятно, кого искать. Редкое исключение — поиск ближайшего живого узла.

      

    

    

    
Команда и событие — главная путаница. Команда — «сделай»: адресована одному, может получить отказ. Событие — «случилось»: адресовано никому конкретно, отклонить его нельзя, факт уже произошёл. Если назвать событие OrderShouldBeShipped («заказ надо отгрузить»), это на самом деле команда. Маскировка под факт лишает систему возможности вернуть отказ — его просто некому отправить.

глава 6 · очередь изнутри талончики, подтверждения и неудачники

    
Вспомним поликлинику. Пациенты берут талоны, врачи вызывают по одному. Если пришло сразу много людей, очередь растёт, но никто не уходит ни с чем. Если открыть второй кабинет, очередь тает быстрее. Очередь сообщений устроена так же. Вот три её главных правила.

    

      
1. Очередь — буфер
Отправитель кладёт задачу и свободен. Пик в 12 задач не роняет обработчика: они подождут.

      
2. Подтверждение (ack)
Задача удаляется из очереди, только когда обработчик сказал «готово». Упал посреди работы — задача вернётся и достанется другому.

      
3. Очередь неудачников
Задача, которая падает раз за разом, после трёх попыток уезжает в отдельную очередь (dead letter queue, DLQ), чтобы не крутиться вечно.

глава 9 · GraphQL подробно кто решает, какие поля нужны

    
Частый вопрос: «В REST летит JSON, в GraphQL тоже летит JSON. В чём разница?» Разница не в формате, а в том, кто решает, что будет в ответе.

    

      

        
🍱 REST: комплексный обед

        
У сервера много адресов: /orders/77, /couriers/9. Каждый отдаёт свой фиксированный набор полей. Лишнее приходится выбрасывать (перевыборка, over-fetching). Недостающее — добирать новыми запросами (недовыборка, under-fetching).

      

      

        
🧑‍🍳 GraphQL: заказ à la carte

        
Адрес один: /graphql. У сервера есть схема — типизированное описание всех данных и связей между ними. Клиент присылает запрос в виде «формы» ответа, и сервер возвращает ровно её. Ни полем больше.

Что внутри: схема и резолверы

    
Схема — контракт GraphQL: какие есть типы, поля и связи. Резолвер — маленькая функция, которая умеет достать одно поле. Сервер проходит по запросу клиента и для каждого поля вызывает его резолвер.

    

      
type Query {
  order(id: ID!): Order
}

type Order {
  id: ID!
  status: OrderStatus!
  total: Int!
  createdAt: String!
  items: [OrderItem!]!
  courier: Courier        # живёт в сервисе доставки
  customer: Customer!     # живёт в сервисе клиентов
}

type OrderItem {
  title: String!
  qty: Int!
  price: Int!
  photo: String
}

type Courier  { name: String!  phone: String  eta: String }
type Customer { name: String! }

      
const resolvers = {
  Query: {
    // GET /orders/:id в сервисе заказов
    order: (_, { id }) => ordersApi.get(id),
  },
  Order: {
    items:    o => ordersApi.items(o.id),
    // два вызова внутри: доставка → курьер
    courier:  o => delivery.courierFor(o.deliveryId),
    customer: o => customersApi.get(o.customerId),
  },
  OrderItem: {
    title: it => catalogLoader.load(it.sku)
                   .then(p => p.title),
  },
};

// Резолвер вызывается ТОЛЬКО для полей,
// которые клиент попросил.
// Не спросили courier — в доставку не ходим.

    

    
Важно понимать. GraphQL не отменяет походов между сервисами. Те же вызовы делает сервер — внутри дата-центра, близко и параллельно. Клиент же делает один запрос по медленной мобильной сети. Выигрыш — в числе походов по «длинному» участку и в объёме трафика.


    
Честные минусы

    
1. Проблема N+1. Экран «мои заказы» показывает 10 заказов и курьера у каждого. Резолвер courier вызывается для каждого заказа отдельно: 1 запрос за списком + 10 за курьерами. Лечится загрузчиком пачками — DataLoader: он копит вызовы и делает один общий.

    

    

    

    

    
2. Дорогие запросы. Клиент сам строит запрос, значит, может построить и очень тяжёлый: вложить списки друг в друга. Каждый уровень умножает число объектов. Двигайте глубину.

    
глубина вложенности2

    

      

      

    

    

      
3. Кеширование по HTTP не работает
В REST у каждого ресурса свой адрес, и прокси или браузер кешируют GET /orders/77 сами. В GraphQL всё идёт через один POST /graphql с разными телами. Стандартный кеш тут бессилен. Выручают сохранённые запросы (persisted queries) и кеш на клиенте — но это ещё работа.

      
4. Права доступа на уровне полей
В REST права проверяют на адресе: «этот эндпоинт — только для менеджеров». В GraphQL один адрес, а запрос может дотянуться через связи куда угодно: order → customer → phone. Права приходится проверять в каждом резолвере, иначе клиент вытащит чужой телефон через соседнее поле.

    

    
Когда брать GraphQL. Много разных клиентов (веб, iOS, Android), экраны собирают данные из нескольких сервисов, важен объём трафика. Обычно GraphQL ставят как отдельный слой между клиентами и сервисами (BFF — backend for frontend, «бэкенд для конкретного фронтенда»). Когда не брать: один клиент и десяток простых ручек, межсервисные вызовы, файлы и потоки.

глава 12 · контракты о чём договорились и как это менять

    
Когда Заказы звонят Складу, оба заранее договорились: куда звонить, какие поля отправить, что придёт в ответ. Эта договорённость называется контракт. Для REST её записывают в OpenAPI — файл с описанием запросов и ответов, для gRPC — в файл .proto, для событий — в схему события.

    
Главное правило распределённых систем: вы не решаете, когда соседи обновят свой код. У мобильного приложения старые версии живут месяцами на телефонах, которые никто не обновляет. Значит, любое изменение контракта должно быть обратно совместимым: старый потребитель продолжает работать. Несовместимое изменение разбивают на несколько совместимых шагов.

Цикл «расширь — мигрируй — сузь» (expand / contract)

    

      
1
Расширь. Добавляем новое поле рядом со старым. Сервис пишет в оба, читает старое. Ничего не ломается.Пример: было name, добавили fullName.

      
2
Мигрируй. Потребители по одному переходят на новое поле в своём темпе. Старое ещё живо.Нужен способ узнать, кто ещё читает старое поле: метрика обращений или журнал по потребителям.

      
3
Сузь. Когда старое поле никто не читает, его удаляют.Этот шаг откладывают навсегда. Ставьте дату удаления сразу на первом шаге, иначе через три года у вас сорок полей и половина не используется.

    

    
Про версии в адресе. /v2/orders — не спасение, а отсрочка. Две версии — это две ветки кода, два набора тестов и двойная поддержка. Удалить v1 всё равно нельзя, пока на ней кто-то сидит. Версия в адресе оправдана для крупной переделки раз в несколько лет. Повседневные изменения делают совместимыми шагами.

    
Как ловить поломку до выкатки. Контрактные тесты: потребитель описывает, какие поля ему действительно нужны, а сборка поставщика падает, если изменение их ломает (consumer-driven contracts, инструмент Pact). Несовместимость обнаруживается у автора изменения, а не в проде у соседа через две недели.

  


  
  

    
глава 13 · идемпотентность повтор не должен удваивать

    
Сеть ненадёжна. Запрос может дойти, а ответ — потеряться. Клиент не знает, что случилось, и повторяет. Анна может дважды нажать кнопку. Брокер может доставить сообщение второй раз. Во всех этих случаях сервер получает одну и ту же просьбу дважды.

    
Определение. Операция идемпотентна, если её повтор даёт тот же результат, что и первый раз. «Поставь лампочку в положение “выкл”» — идемпотентно: сколько ни нажимай, лампочка выключена. «Переключи лампочку» — нет: каждое нажатие меняет результат. «Спиши 4 200 ₽» — тоже нет: два запроса спишут 8 400 ₽.

    
Стандартное решение — ключ идемпотентности. Клиент придумывает уникальный номер для каждого намерения («оплатить заказ ord-77») и присылает его в заголовке. Сервер запоминает ключ и ответ. Если ключ пришёл снова, сервер не делает работу повторно, а отдаёт сохранённый ответ.

Идемпотентны сами по себе
GET, PUT с полным состоянием, DELETE. Повтор не меняет результат.

      
Требуют ключа
POST на создание, любое «добавь», «спиши», «начисли». Повтор создаёт дубль.

      
Частая ошибка
Отвечать на повтор ошибкой «уже существует». Клиент не отличит «мой повтор» от «чужого конфликта». Правильно — вернуть тот же ответ.

    

    
В обработчиках сообщений работает тот же приём: у каждого сообщения есть messageId или eventId. Обработчик записывает обработанные номера и пропускает уже виденные. Так «хотя бы один раз» от брокера превращается в «ровно один раз» по результату.
