Способ связи выбирают двумя вопросами: ждём ли мы ответ прямо сейчас и знаем ли, кому звоним. Получается четыре сочетания. Почти все ошибки интеграции — это попытка решить задачу из одного угла средствами другого.

Синхронно, знаю получателя — запрос-ответ

«Дай мне баланс», «зарезервируй товар». REST, gRPC, GraphQL. Ответ нужен для продолжения работы.

Цена: звено в цепочке доступности, задержка в хвосте, связность по адресу и контракту.

Асинхронно, знаю получателя — команда в очередь

«Сформируй отчёт», «отправь письмо». Очередь конкретному обработчику, ответа не ждём.

Цена: нужен способ узнать результат — статус, колбэк или уведомление.

Асинхронно, не знаю получателей — событие

«Заказ оформлен». Публикуем факт, кто заинтересован — подпишется. Издатель о подписчиках не знает.

Цена: процесс не виден целиком, отложенная согласованность, обязательная идемпотентность.

Синхронно, не знаю получателя — почти всегда ошибка

«Спрошу у всех, кто ответит». Встречается в виде широковещательных запросов и «запрос-ответ через брокер».

Почему плохо: доступность зависит от самого медленного, а отладка невозможна. Редкое исключение — поиск ближайшего живого узла.

Правило большого пальца: команда — «сделай» (адресована одному, может быть отклонена), событие — «случилось» (адресовано никому конкретно, отклонить нельзя, факт уже произошёл). Путаница между ними — источник половины проблем в событийных системах: событие OrderShouldBeShipped на самом деле команда, и её маскировка под факт лишает систему возможности вернуть отказ.

эволюция как менять контракт, не ломая потребителей

Главное правило распределённых систем: вы не контролируете момент обновления потребителей. Значит, любое изменение обязано быть обратно совместимым, а несовместимое — разбито на несколько совместимых шагов.

Совместимые изменения

  • Добавить необязательное поле в ответ.
  • Добавить необязательное поле в запрос со значением по умолчанию.
  • Добавить новую ручку или новый тип события.
  • Ослабить валидацию (принимать больше, чем раньше).

Ломающие изменения

  • Удалить или переименовать поле.
  • Сменить тип или формат (строка → число, дата с таймзоной → без).
  • Сделать необязательное поле обязательным.
  • Изменить смысл значения при том же имени — худший случай: ничего не сломается сразу, всё сломается тихо.

Цикл «расширь — мигрируй — сузь» (expand / contract)

1
Расширь. Добавляем новое поле рядом со старым. Сервис пишет в оба, читает старое. Ничего не ломается.Пример: было name, добавили firstName + lastName.
2
Мигрируй. Потребители по одному переходят на новое поле в своём темпе. Старое ещё живо.Здесь нужен способ узнать, кто ещё читает старое поле: метрика обращений или логирование по потребителям.
3
Сузь. Когда старое поле никто не читает, оно удаляется.Это тот шаг, который откладывают навсегда. Ставьте дату сразу на шаге 1, иначе через три года у вас сорок полей и половина не используется.
Про версионирование: /v2/orders — не спасение, а отсрочка. Две версии означают две ветки кода, два набора тестов и удвоенную поддержку; и удалить v1 всё равно нельзя, пока на нём кто-то есть. Версия в URL или заголовке оправдана для крупных редизайнов раз в несколько лет. Повседневная эволюция — через совместимые изменения, а не через новые версии.

обязательно идемпотентность запросов на изменение

Клиент отправил «создать платёж», не получил ответа и повторил. Создать второй платёж нельзя. Стандартное решение — ключ идемпотентности: клиент генерирует уникальный идентификатор попытки и присылает его в заголовке.

POST /payments
Idempotency-Key: 3f1c8a2e-4b7d-4f11-9c2a-77e0d1b6a904
Content-Type: application/json

{"orderId": "ord-77", "amount": 4200, "currency": "RUB"}

// Сервер:
// 1) кладёт ключ в таблицу с уникальным индексом;
// 2) если вставка не прошла — операция уже выполнялась:
//    возвращает СОХРАНЁННЫЙ ответ первой попытки, а не новый;
// 3) ключ живёт ограниченное время (обычно 24 часа).

Естественно идемпотентные

GET, PUT с полным состоянием, DELETE. Повтор не меняет результат.

Требуют ключа

POST на создание, любое «добавь», «спиши», «начисли». Повтор создаёт дубль.

Частая ошибка

Возвращать на повтор ошибку «уже существует». Клиент не различит «мой повтор» и «чужой конфликт». Правильно — вернуть тот же ответ.
