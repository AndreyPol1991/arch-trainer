Между двумя частями системы всегда есть отношения. Кто диктует формат, кто подстраивается, кто от кого защищается переводчиком. Если эти отношения не назвать вслух, они сложатся сами — и обычно в форме «мы подстраиваемся под всех».

зачем это зачем рисовать карту контекстов

зачем это вообще отношение — это не про код, это про людей

Самое непонятное место во всей теме. Давайте начистоту: отношение между контекстами — это договорённость двух команд о том, кто под кого подстраивается. Всё. Никакой техники.

Житейски. Вы снимаете квартиру. Между вами и хозяином есть отношение: кто устанавливает правила, кто может их менять, кто обязан подстроиться. Можно этого не проговаривать — но тогда однажды выяснится, что хозяин считал иначе. Обычно в неудобный момент.

Вопрос, на который отвечает отношение

Он всего один, и звучит так:

«Команда А меняет формат ответа. Кто обязан переделывать — и когда?»

Пока ответа нет, каждое изменение превращается в переговоры с нуля, а иногда и в скандал. Когда ответ записан заранее — это просто рабочая процедура.

как выглядит сама карта контекстов — вот она

Сначала о том, что вообще имеется в виду под словом «карта». Это буквально схема на стене: коробки — части системы, стрелки — кто с кем разговаривает, подписи на стрелках — какие между ними отношения.

Вот и всё, что такое карта контекстов. Одна картинка, на которой видно: кто с кем связан, в какую сторону, и по каким правилам. Её рисуют на доске за час и вешают там, где её видно команде.
Что значит «повесить на видное место». Буквально: распечатать или вывесить в вики, чтобы новый человек увидел её в первый день, а не собирал эту картину по кусочкам три месяца. Это самое частое и самое недооценённое применение карты.

подробно слой предотвращения порчи (ACL) — как он выглядит в коде

Это самый нужный из восьми паттернов и единственный, который вы будете применять почти в каждой интеграции. Его смысл: чужая модель не должна проникать внутрь вашего контекста. Всё, что приходит снаружи, на границе переводится в ваши понятия; всё, что уходит, — в чужие.

// ─── Плохо: чужая модель растеклась по всему коду ───
// Классы сгенерированы из чужого WSDL и используются напрямую.
class OrderService {
  void ship(ExternalShipmentResponseTypeV2 resp){   // чужое имя в нашем коде
    if("SHP_ST_04".equals(resp.getStatusCode())){  // чужая магия
      order.setStatus("SHIPPED");
    }
  }
}
// Последствия: смена перевозчика = правки по всей кодовой базе;
// значение "SHP_ST_04" знают в шести местах; тесты требуют чужих классов.

// ─── Хорошо: переводчик на границе ───
interface ShippingGateway {                    // НАШ контракт, наши слова
  ShipmentStatus statusOf(OrderId id);           // наш enum, наш тип
}

class DhlShippingAdapter implements ShippingGateway {  // ACL
  public ShipmentStatus statusOf(OrderId id){
    var resp = dhlClient.track(id.value());     // чужое живёт только здесь
    return switch(resp.getStatusCode()){       // перевод один раз, в одном месте
      case "SHP_ST_04", "SHP_ST_05" -> ShipmentStatus.DELIVERED;
      case "SHP_ST_02"            -> ShipmentStatus.IN_TRANSIT;
      default                       -> ShipmentStatus.UNKNOWN;
    };
  }
}
// Смена перевозчика = новая реализация интерфейса. Остальной код не знает,
// что перевозчик вообще менялся. Тесты домена работают на заглушке.

Когда ACL обязателен

  • Интеграция с покупной или legacy-системой, чью модель вы не контролируете.
  • Внешний партнёр, который меняет контракт без предупреждения.
  • Общий поддомен, который вы планируете однажды заменить.
  • Любой контекст, где «их» слова не совпадают с «вашими».

Когда ACL — лишняя работа

  • Внутренний сервис вашей же команды с общим языком: перевод получится тождественным.
  • Контракт стабилен и спроектирован специально для потребителей (см. «Открытая служба»).
  • Интеграция одноразовая и будет выброшена через месяц.
