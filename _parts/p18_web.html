глава 1 · завязка «на телефоне всё тормозит»: что вообще делает фронтенд

Пятница. Аналитик Олег разбирает отзывы покупателей «Ботинка». Три жалобы повторяются чаще других: «карточка товара на телефоне открывается вечность», «нажимаю размер — ничего не происходит», «пока читала описание, кнопка прыгнула вниз, и я нажала на баннер». Ведущая фронтенд-разработчица Вера молча открывает статистику: у трёх четвертей покупателей — телефон, у половины из них — недорогой.

Кто прав? Оба. Чтобы понять почему, начнём с самых основ.

Фронтенд (frontend) — часть системы, которая работает на устройстве пользователя и рисует интерфейс: страницы сайта, экраны приложения, кнопки, формы. Бэкенд (backend) — часть, которая работает на серверах компании: хранит данные, считает цены, принимает заказы.
ресторан. Кухня — бэкенд: там готовят, и гость её не видит. Зал — фронтенд: меню, столы, официант, счёт. Можно готовить божественно, но если меню несут двадцать минут, а официант не слышит, гость уйдёт.
Браузер — программа, которая по адресу скачивает страницу, понимает три языка — HTML, CSS и JavaScript — и рисует результат. Chrome, Safari, Firefox, Яндекс Браузер, Edge — всё это браузеры. Мобильное приложение — тоже фронтенд, только рисует его не браузер, а сама операционная система телефона.

HTML — что на странице

Разметка: заголовок, картинка, цена, кнопка «В корзину». Это содержание и его структура.

CSS — как выглядит

Оформление: цвета, шрифты, отступы, раскладка на телефоне и на компьютере. Без CSS страница — чёрный текст на белом фоне в один столбик.

JavaScript — что делает

Поведение: что случится при нажатии, как обновится корзина, как подгрузятся отзывы. На JavaScript пишут и целые приложения, которые рисуют страницу сами.

дом. HTML — стены и комнаты. CSS — обои, мебель и шторы. JavaScript — электрика: нажали выключатель — загорелся свет. Без проводки в доме можно жить, но свет не включится.
DOM (Document Object Model, объектная модель документа) — дерево объектов, которое браузер строит из HTML. У каждого элемента страницы — свой узел: «заголовок», «картинка», «кнопка». JavaScript меняет страницу, меняя DOM, а браузер перерисовывает то, что изменилось.
HTML — чертёж квартиры, DOM — макет этой квартиры на столе у прораба. Чертёж прочитали один раз и по нему собрали макет. Дальше JavaScript переставляет мебель прямо в макете, а чертёж уже никто не открывает.

Главная аналогия раздела: сборка шкафа

Страница приходит к Анне как шкаф из мебельного магазина. Есть инструкция (HTML), краска и фурнитура (CSS), моторчик для выдвижных ящиков (JavaScript) и сами детали — фотографии и данные о товаре. Всё решает, что приезжает первым и кто собирает:

Инструкция раньше деталей

Привезли инструкцию, а детали едут отдельной машиной. Можно разложить коробки, но шкаф не собрать. Так работает отрисовка в браузере (CSR): сначала приходит код, потом он сам идёт за данными.

Инструкция вместе с деталями

Всё в одной коробке. Собирать можно сразу. Так работает многостраничный сайт: сервер присылает готовую страницу с текстом и ссылками на картинки.

Шкаф привозят собранным

Его сразу видно и можно поставить вещи. Но моторчик ящиков подключат через полчаса: до этого ящики не выдвигаются. Так работает серверная отрисовка с гидрацией (SSR) — об этой ловушке вся глава 4.

глава 2 · путь отрисовки от адреса до пикселей: что делает браузер и что ему мешает

Анна нажала на ссылку. Как найти сервер и установить соединение, разобрано в разделе . Здесь начинаем с момента, когда первые байты HTML уже летят к телефону. Дальше браузер проходит одну и ту же цепочку шагов. Её называют критическим путём.

Критический путь отрисовки (critical rendering path) — последовательность шагов, через которые браузер проходит от байтов HTML, CSS и JavaScript до пикселей на экране: построить DOM, построить CSSOM, сложить из них дерево отрисовки, рассчитать раскладку, нарисовать и склеить слои.
сборка шкафа по инструкции. Инструкцию (HTML) можно читать по мере того, как приходят страницы. Но красить (CSS) нельзя, пока не привезли краску: иначе всё придётся перекрашивать. А пункт «стоп, позвоните мастеру и ждите его» посреди инструкции (скрипт без defer) останавливает всю сборку, даже если мастер нужен только для одного ящика.

DOM

Дерево элементов из HTML. Браузер строит его потоково: разбирает HTML кусками, по мере прихода байтов, не дожидаясь конца файла.

CSSOM

CSS object model — дерево правил оформления. Строится только из целого файла стилей: последнее правило может переопределить первое.

Дерево отрисовки

Render tree — DOM плюс CSSOM, но только видимые элементы. Скрытое через display:none в него не попадает.

Раскладка

Layout (в Firefox — reflow): точные размеры и координаты каждого элемента под ширину экрана.

Отрисовка

Paint: пиксели — текст, цвета, рамки, картинки. Рисуется по слоям.

Склейка слоёв

Composite: слои складываются в итоговый кадр, обычно силами видеокарты. Анимации через transform трогают только этот шаг — поэтому они плавные.

Кто блокирует экран

CSS блокирует отрисовку

Пока не скачан и не разобран каждый файл стилей из <head>, браузер не рисует ничего. Иначе Анна на миг увидела бы страницу без оформления, а потом она бы «перепрыгнула». Поэтому стили — render-blocking: блокирующие отрисовку.

Обычный скрипт блокирует разбор

<script src> без атрибутов останавливает разбор HTML: браузер обязан скачать и выполнить скрипт сразу, ведь тот может поменять страницу. Скрипт ещё и ждёт стили — вдруг он спросит размеры элементов. Это parser-blocking: блокирующий разбор.

defer

Скачать параллельно, выполнить после разбора всего HTML, по порядку. Выбор по умолчанию для своих скриптов. Скрипты-модули (type="module") ведут себя так же.

async

Скачать параллельно, выполнить, как только скачался, в любом порядке. Для независимых скриптов: аналитика, пиксели рекламы.

Предзагрузчик

Preload scanner: пока основной разбор стоит, отдельный «разведчик» заглядывает вперёд по HTML и заранее запрашивает картинки, стили и скрипты. Поэтому то, что написано в HTML, находится быстро, а то, что создаёт JavaScript, — поздно.

глава 3 · способы отрисовки кто и когда собирает страницу: девять способов

Главный архитектурный вопрос фронтенда звучит так: где и когда HTML превращается из данных в разметку? На сервере при каждом запросе, на сервере заранее, в браузере — или понемногу везде. От ответа зависят первый показ, поисковики, нагрузка на сервер и сложность. Разберём девять способов от старого к новому. Почти все они живут в современных фреймворках: Next.js, Nuxt, SvelteKit, Astro, Angular и других.

Отрисовка (rendering) во фронтенде — превращение данных и шаблонов в HTML (или сразу в DOM). Не путать с отрисовкой пикселей из главы 2: там браузер рисует готовый HTML, а здесь кто-то этот HTML создаёт.
Гидрация (hydration) — оживление готового HTML в браузере. Сервер прислал страницу, её уже видно. Затем браузер скачивает тот же код компонентов, заново «проходит» по ним, сверяет с HTML и подключает обработчики нажатий. До конца гидрации кнопки нарисованы, но не работают.
в магазин привезли собранный шкаф — его сразу видно. Но моторчики ящиков подключит электрик, который едет следом. Пока он не приехал и не проверил каждый ящик, ящики не выдвигаются, сколько ни тяни.

1. MPA multi-page application

Многостраничный сайт: каждый переход — новый запрос, сервер собирает HTML по шаблону (PHP, Java, Python, .NET), браузер рисует. JavaScript — немного, для мелочей.

ресторан с комплексными обедами: каждое блюдо приносят готовым на новой тарелке.

Плюсы: полный HTML сразу, отлично для поисковиков, мало кода в телефоне, формы работают даже без JavaScript. Минусы: каждый переход — перезагрузка страницы, богатые интерактивные экраны собирать трудно. Когда: контентные сайты, каталоги, госуслуги, магазины с простым интерфейсом.

2. SPA и CSR client-side rendering

Одностраничное приложение: сервер отдаёт почти пустой HTML и большой JavaScript. Страницу рисует браузер, данные идут по API. Переходы — без перезагрузки: код меняет DOM и адрес в строке.

шкаф с инструкцией, но детали едут отдельной машиной: сначала код, потом он сам идёт за данными.

Плюсы: быстрые переходы после загрузки, богатый интерфейс, сервер отдаёт только данные и статику. Минусы: пустой HTML для поисковиков и превью ссылок, долгий первый показ на слабом телефоне, весь код — в телефоне. Когда: за логином: личный кабинет, админки, редакторы, внутренние системы.

3. SSR + гидрация server-side rendering

Те же компоненты, что в SPA, но первый HTML собирает сервер — на каждый запрос, с данными. Браузер показывает его сразу, потом скачивает JavaScript и гидрирует. Дальше работает как SPA.

шкаф привозят собранным, электрик для ящиков едет следом.

Плюсы: быстрый первый показ, полный HTML для поисковиков, свежие данные. Минусы: нужен сервер с Node.js и нагрузка на каждый запрос, двойная работа (отрисовка на сервере и гидрация в браузере), «мёртвая зона» до конца гидрации, сервер ждёт самые медленные данные. Когда: публичные страницы с личным или часто меняющимся содержимым и важным SEO.

4. SSG static site generation

Страницы собираются заранее, при сборке проекта, и лежат готовыми HTML-файлами на CDN. Сервер на каждый запрос не нужен.

шкафы собраны на складе заранее и стоят в зале — бери и неси.

Плюсы: самый быстрый ответ, почти бесплатная раздача, нечему падать. Минусы: данные — на момент сборки; 50 000 карточек собираются долго; цену и остаток всё равно догружает браузер. Когда: документация, справка, блог, лендинги акций.

5. ISR и stale-while-revalidate incremental static regeneration

Как SSG, но готовая страница обновляется сама: у неё есть срок свежести. Первый запрос после истечения срока получает старую страницу, а в фоне собирается новая. ISR — термин Next.js; то же даёт заголовок HTTP Cache-Control: s-maxage=60, stale-while-revalidate=600 на CDN (RFC 5861).

витрина булочной: выставили утренний хлеб; когда партия «устарела», продавец продаёт пока что есть, а пекарь в это время печёт новую.

Плюсы: скорость SSG и почти свежие данные, не надо пересобирать весь сайт. Можно обновить страницу по событию — например, когда товаровед поменял цену. Минусы: кто-то увидит устаревшее, логика кеша сложнее. Когда: карточки товаров, каталог, новости.

6. Стриминг SSR streaming

Сервер не ждёт всех данных. Сразу отправляет «скелет» страницы с шапкой, а медленные блоки дописывает в тот же ответ, когда они готовы. В React это делается через <Suspense>: вместо медленного блока сначала приходит заглушка.

официант сразу приносит хлеб и салат, а горячее — когда оно готово, не держа весь стол голодным.

Плюсы: первый байт и первый показ не ждут медленные рекомендации; гидрация идёт по блокам. Минусы: код ответа и заголовки уходят в самом начале — потом не сделать 404 или редирект; посредник с буферизацией может «склеить» поток; сложнее отладка. Когда: SSR-страницы, где есть быстрые и медленные блоки.

7. Островная архитектура islands, Astro

Страница — статический HTML, а интерактивны только отдельные «острова»: галерея, кнопка корзины, калькулятор размера. Каждый остров гидрируется сам и только когда нужно: в Astro — client:load, client:idle, client:visible. С Astro 5 есть и серверные острова (server:defer): страница из кеша, а личный блок дорисует сервер.

в музее все экспонаты за стеклом, и только у пары стендов есть кнопки «нажми меня». Электричество нужно только им.

Плюсы: очень мало JavaScript, отличный первый показ. Минусы: острова плохо делят общее состояние, для приложения с множеством связанных экранов неудобно. Когда: контентные сайты, блоги, маркетинговые страницы.

8. React Server Components RSC

Компоненты делятся на серверные и клиентские. Серверные выполняются только на сервере: могут читать базу и API, а их код не попадает в браузер. Клиентские помечаются директивой "use client" — только они гидрируются. Стабильны в React 19 (декабрь 2024), основная реализация — App Router в Next.js. В Next.js 16 (октябрь 2025) к ним добавили явное кеширование директивой "use cache".

шкаф собран на складе, а электрик приезжает только к двум выдвижным ящикам, а не проверяет каждую полку.

Плюсы: меньше JavaScript в телефоне, данные берутся рядом с базой, стриминг из коробки. Минусы: новая модель мышления (что где выполняется), привязка к фреймворку, нужен Node.js-сервер, сложнее кеширование и отладка. Когда: новые проекты на React с публичными страницами и богатыми данными.

9. Edge-рендеринг на краю сети

SSR выполняется не в одном дата-центре, а на узлах CDN рядом с пользователем (Cloudflare Workers и аналоги у других облаков и хостингов). Окружение урезанное: стандартные веб-API вместо полного Node.js, лимиты на время и память.

Плюсы: короткий круг до пользователя: проверка входа, редиректы, A/B-тесты и персонализация по городу. Минусы: база данных обычно в одном регионе — каждый запрос с края к базе в Москве идёт через всю страну, и несколько таких запросов подряд выходят медленнее, чем отрисовка рядом с базой. Когда: лёгкая логика без тяжёлых данных; рисовать лучше там, где лежат данные.

Проще говоря о гидрации. Гидрация — это цена, которую платят за «HTML сразу + приложение потом». Сервер уже нарисовал страницу, но браузер всё равно должен скачать код всех компонентов и пройти по ним, чтобы подключить обработчики. Острова и Server Components уменьшают эту цену: гидрируется не вся страница, а только интерактивные куски. Есть и подход совсем без гидрации — возобновляемость (resumability) во фреймворке Qwik: обработчики подгружаются в момент первого нажатия.

Их называют Core Web Vitals — «основные показатели качества страницы». Вера открывает отчёт сборки: на первую страницу сайта уходит 700 КБ сжатого JavaScript. Бандл (bundle) — файл или набор файлов, в которые сборщик (Vite, webpack, Rspack, Turbopack) склеивает код приложения и библиотек. Размер считают дважды: сжатый — сколько едет по сети, и несжатый — сколько браузер разбирает и выполняет.
чемодан в отпуск. Есть вес на весах в аэропорту — это сжатый размер, за него платит сеть. И есть вещи, которые потом надо разложить по полкам в номере, — это несжатый размер, за него платит процессор телефона.

Разделение кода (code splitting)

Сборщик режет бандл на куски (chunks). Каждой странице — только её код: каталог не качает код личного кабинета. Делается через динамический import() — обычно по маршрутам.

Ленивая загрузка (lazy loading)

Тяжёлый блок грузится, только когда он нужен: графики — при открытии вкладки «Отзывы», редактор — по кнопке «Написать отзыв», чат — по нажатию на значок. Для картинок ниже первого экрана — loading="lazy".

Удаление мёртвого кода (tree shaking)

Сборщик выбрасывает функции библиотек, которые никто не импортирует. Работает с ES-модулями: import { debounce } from 'lodash-es' — да, «весь lodash одним объектом» — нет.

Сжатие

Сервер или CDN сжимает текстовые файлы: gzip — везде, Brotli — обычно на 15–20 % меньше gzip для JavaScript и CSS, в Chromium и Firefox есть ещё zstd. Сжатие уменьшает дорогу по сети, но не работу процессора: разбирать всё равно несжатое.

Шрифты

Формат WOFF2, только нужные символы (кириллица и латиница, а не все языки мира), font-display: swap — показать текст системным шрифтом, пока качается фирменный. Иначе браузер может прятать текст до трёх секунд.

Подсказки: preload и preconnect

Предзагрузка следующей страницы

<link rel="prefetch"> скачивает то, что понадобится на следующей странице, в свободное время. В Chromium-браузерах есть Speculation Rules API: страницу можно даже заранее отрисовать в фоне, и переход станет мгновенным. Фреймворки сами предзагружают ссылки, попавшие в экран.

глава 7 · водопад водопад запросов: шесть виджетов на одной странице

Откуда берутся ступеньки

Компонент внутри компонента

Родитель загрузил данные и только потом отрисовал детей. Дети начинают свою загрузку после этого. Глубина дерева = число ступенек. Самая частая причина.

Код, потом данные

Ленивый кусок кода сначала скачивается, и только после выполнения узнаёт, какие данные ему нужны. Код → данные → картинка: три ступеньки подряд.

Настоящая зависимость

Чтобы спросить сроки доставки, нужен город Анны, а он — в профиле. Рекомендации нужны «по категории товара». Это честная ступенька, но её можно пройти на сервере, где круг стоит 1 мс, а не 150.

Шесть блоков — восемь запросов из браузера. Каждый со своими заголовками, cookie, проверкой токена. Это тот же N+1, что в базе данных, только по мобильной сети.

BFF глазами фронтенда

BFF (Backend for Frontend, «бэкенд для фронтенда») — небольшой сервер под конкретный клиент: у сайта свой, у мобильного приложения свой. Он собирает данные из сервисов и отдаёт ровно то, что нужно экрану.

Что даёт фронтенду

Один запрос на экран вместо восьми. Форма данных — под экран, а не под схему базы. Можно менять ответ вместе с выпуском фронта, ни с кем не согласовывая. Здесь же хранятся токены доступа: браузеру — только cookie (раздел , глава о браузере).

Кто владеет

Команда фронтенда. Если BFF правит команда бэкенда по заявкам, он превращается в обычный API с лишним прыжком. Обычно BFF пишут на TypeScript рядом с фронтом — часто это просто серверная часть Next.js или Nuxt.

Чем опасен

Расползается: туда утекает бизнес-логика («скидка считается в BFF сайта»), и у сайта и приложения начинаются разные цены. Правило: BFF собирает и перекладывает, но не решает. Для мобильного BFF помните: старые версии приложения живут месяцами — ответ должен оставаться совместимым.

Серверные данные — это кеш: TanStack Query и SWR

Кеш запросов (query cache) — хранилище ответов сервера в браузере, где у каждого ответа есть ключ (например, ['product', 42]), время получения и срок свежести. Библиотеки TanStack Query (версия 5) и SWR берут на себя: показать сохранённое сразу, тихо обновить в фоне, не слать два одинаковых запроса одновременно, повторить после сбоя, обновить при возврате на вкладку и при восстановлении сети.

Оптимистичное обновление

Оптимистичное обновление (optimistic update) — интерфейс показывает результат действия сразу, не дожидаясь ответа сервера, а если сервер ответил ошибкой — откатывает и честно сообщает.

Где нельзя. Оплата, оформление заказа, списание бонусов — всё, где «показали успех, а потом откатили» обманывает человека и может стоить денег. Оптимизм — для лайков, избранного, отметок «прочитано», порядка в списке.

глава 9 · состояние где хранить состояние и кто источник правды

Борис добавил товар в корзину. Цифра в шапке обновилась, а в выпадающей мини-корзине — нет. Олег открыл ссылку, которую прислала Анна, — и увидел каталог без её фильтров. Обе беды — про состояние.

Состояние (state) — данные, которые меняются, пока человек пользуется интерфейсом, и от которых зависит, что нарисовано: открыто ли меню, что лежит в корзине, какой фильтр выбран, что набрано в поле.
доска в учительской: расписание, кто заболел, где ключ от спортзала. Если у каждого учителя своя копия на бумажке, к обеду копии разойдутся, и двое придут в один кабинет.
Источник правды (single source of truth) — у каждого факта ровно одно место, где он «настоящий». Всё остальное — производные значения или кеши с правилами обновления. Хотите узнать правду — идёте туда, а не к копии.

Пять мест для состояния

🗄 Серверное

Принадлежит серверу: товары, цены, корзина, заказы, профиль. У фронта — только кеш (глава 8). Инструменты: TanStack Query, SWR, RTK Query, Apollo Client.

🔗 В адресе (URL)

То, чем хочется поделиться ссылкой и что должно пережить обновление страницы и кнопку «назад»: фильтры, сортировка, номер страницы, поисковый запрос, открытая вкладка.

🌍 Глобальное клиентское

Нужно многим далёким компонентам и не живёт на сервере: тема, язык интерфейса, открыт ли чат, очередь уведомлений-«тостов». Его обычно мало.

📍 Локальное

Нужно одному компоненту: раскрыт ли список размеров, наведён ли курсор, какой слайд галереи. Живёт внутри компонента и умирает вместе с ним.

📝 Состояние формы

Черновик ввода, ошибки проверки, «поле трогали», «форма отправляется». Отдельные библиотеки (React Hook Form) и схемы проверки (Zod) — те же правила проверки можно использовать и на сервере.

💾 Постоянное в браузере

localStorage, IndexedDB, cookie: переживает закрытие вкладки. Для настроек и черновиков. Для токенов — нет (глава 13).

Только вниз

глава 12 · офлайн и PWA метро, тоннель, дача: сайт, который работает без сети

Анна едет в метро. Между станциями сеть пропадает. Мобильное приложение «Ботинка» показывает каталог и избранное — данные сохранены. А сайт показывает браузерную заглушку «Нет подключения к интернету». Олег спрашивает: «Нам обязательно делать приложение, чтобы работать без сети?» Нет — для многого хватит браузера.

PWA (progressive web app, прогрессивное веб-приложение) — сайт, который можно установить на домашний экран и который ведёт себя как приложение: свой значок, окно без адресной строки, работа без сети, уведомления. Техническая основа — HTTPS, файл-манифест и service worker.
Service worker — скрипт, который браузер запускает отдельно от страницы. Он стоит между страницей и сетью как посредник: перехватывает каждый запрос и решает, ответить из своего кеша, сходить в сеть или сделать и то и другое. Работает только на HTTPS (и на localhost для разработки).
консьерж в доме. Вы просите свежую газету. Он смотрит, нет ли её у него на столе; если нет — идёт в киоск; если киоск закрыт — отдаёт вчерашнюю и честно говорит, что она вчерашняя.

1. Установка (install)

Страница регистрирует скрипт. Браузер скачивает его и вызывает событие install: здесь заранее кладут в кеш «оболочку» приложения — HTML, стили, скрипты, значки.

2. Активация (activate)

Удаляем кеши прошлых версий. Новая версия service worker по умолчанию ждёт, пока закроют все вкладки со старой, — чтобы на одной странице не смешались две версии. Ускорить можно (skipWaiting), но осознанно.

3. Перехват (fetch)

Каждый запрос страницы проходит через обработчик fetch. Для разных адресов — разные стратегии: статика из кеша, цены из сети, картинки «кеш и обновление».

CORS: кто кому разрешает читать

    
Политика одного источника (same-origin policy) — скрипт со страницы одного источника (схема + домен + порт) не может читать ответы с другого источника. CORS (Cross-Origin Resource Sharing) — способ, которым сервер явно разрешает чтение своих ответов страницам с других источников, через заголовки Access-Control-Allow-*.

    
в бизнес-центре посетитель с пропуском одного офиса не может забрать почту другого офиса. Если другой офис заранее сказал охране «этому соседу почту выдавать можно» — выдадут.

    

    
CORS — не защита сервера. Это защита пользователя в браузере: чтобы чужая страница не прочитала его данные с вашего API от его имени. Запрос из curl или с сервера злоумышленника CORS не остановит. Серверу по-прежнему нужны аутентификация и проверка прав. И никогда Access-Control-Allow-Origin: * вместе с cookie — браузер это и не позволит.


    
CSRF: запрос от имени Анны с чужого сайта

    
CSRF (cross-site request forgery, подделка межсайтового запроса) — злой сайт заставляет браузер Анны отправить запрос на botinok.ru. Браузер приложит её cookie, и сервер решит, что это сделала она: сменила адрес доставки, подписалась, купила.

    
мошенник присылает вам заполненный бланк перевода и просит «просто расписаться внизу». Подпись настоящая — и банк выполнит перевод.

    

      
SameSite у cookie
SameSite=Lax (в Chromium — по умолчанию) или Strict: cookie не уходит с запросами, начатыми чужим сайтом (кроме обычных переходов по ссылке для Lax).

      
Свой заголовок или токен
BFF принимает изменения только с заголовком, который ставит наш код (например, X-Requested-With), или с CSRF-токеном в форме. Чужой сайт не может добавить заголовок к запросу на наш домен без разрешения CORS.

      
Проверка источника
Сервер смотрит заголовки Origin и Sec-Fetch-Site: запрос пришёл со своего сайта или с чужого? Чужой — отказ.

    


    
Цепочка поставок: чужой код, который стал вашим

    
В сайте «Ботинка» 40 прямых зависимостей из npm и больше тысячи косвенных. Плюс скрипты аналитики, чата и рекламы прямо на странице. Каждая из них выполняется с правами вашего кода.

    

      
Как это случается
Июнь 2024, polyfill.io. Домен популярного сервиса полифилов купила другая компания, и скрипт начал подмешивать вредный код на больше чем 100 000 сайтов, которые подключали его напрямую с этого домена.
8 сентября 2025, chalk и debug. Мейнтейнер популярных пакетов npm попался на фишинговое письмо «от поддержки npm». В пакеты с миллиардами скачиваний в неделю на пару часов попал код, подменявший адреса криптокошельков в браузере.

      
Что делать
Файл блокировки версий (lockfile) и npm ci в сборке; новые зависимости — через ревью; автоматический поиск уязвимостей (npm audit, Dependabot, Renovate); не ставить версию в первые дни после выхода; не запускать скрипты установки пакетов без нужды (pnpm 10 по умолчанию их не запускает); список компонентов (SBOM). Сторонние скрипты — хранить у себя или подключать с проверкой целостности.

    

    
SRI (Subresource Integrity, проверка целостности подресурса) — атрибут integrity с хешем файла. Браузер скачает скрипт, посчитает хеш и выполнит, только если хеш совпал. Подменили файл на CDN — браузер его не выполнит.

        integrity="sha384-oqVuAfXRKap7fdgcCY5uykM6+R9GqQ8K/uxy9rx7HNQlGYl1kPzQho1wx4JwY8wC"

Где SRI не поможет. Только для файлов с фиксированным содержимым. polyfill.io отдавал разный код под разные браузеры — хеш к нему не подставить. Поэтому надёжный ответ на такие сервисы — копировать файл к себе и раздавать со своего CDN.

глава 14 · выпуск сборка, CDN, атомарный деплой, флаги и ошибки в проде

Сборка фронтенда (build) — превращение исходников (TypeScript, JSX, модули, стили) в файлы, которые понимает браузер: склейка, минификация, разделение на куски, хеши в именах. В Next.js с версии 16 сборщик по умолчанию — Turbopack.

Артефакт
Статический сайт (SPA, SSG) — это папка файлов: она едет в объектное хранилище и на CDN, сервер не нужен. Для SSR и RSC добавляется серверная часть на Node.js — её упаковывают в контейнер, как любой сервис (раздел ).

      
Одна сборка — много сред
Собираем один раз, а тестовую, предпродакшен и продакшен отличают настройки, которые подставляются при выдаче (например, через /config.json или переменные сервера). Пересобирать «для прода» — значит выпускать не то, что тестировали.

    


    
Атомарный деплой и что ломается без него

    
Атомарный деплой (atomic deploy) — выпуск, при котором пользователи видят либо целиком старую версию, либо целиком новую, и никогда — смесь. Делается так: сначала выкладываются все новые файлы (их имена не пересекаются со старыми благодаря хешам), потом одним действием переключается указатель — какой index.html отдавать. Старые файлы остаются на месте ещё какое-то время.

    
переезд магазина в соседнее здание. Сначала полностью обставляем новое помещение, потом в одну минуту переносим вывеску. Старое помещение не сносим неделю: вдруг кто-то из покупателей ещё внутри.

    
Расхождение версий (version skew) — у пользователя открыта вкладка со старой версией фронтенда, а сервер, CDN и API уже новые. Старая вкладка просит лениво догрузить свой кусок кода — а его удалили; или шлёт запрос в старом формате — а API его больше не понимает.

    
Выберите сценарий выпуска версии v42 вместо v41.

    

    

    
Проще говоря. Новые файлы — до переключения. Переключение — одним действием. Старые файлы — храним дольше, чем живёт самая старая вкладка. API — совместим с предыдущей версией фронта. Откат — то же переключение указателя назад, за секунды, без пересборки.


    
Флаги и A/B-тесты на фронте

    
Основы — в разделе , глава о флагах: выкатить ≠ включить. Особенности фронтенда:

    

      
Мигание
Если флаг или вариант A/B-теста вычисляется в браузере после загрузки, Анна на миг видит старую версию, потом новую. Это портит и впечатление, и CLS. Лечится вычислением на сервере или на краю CDN — вариант приходит уже в HTML.

      
Стандарт и поставщики
OpenFeature — открытый стандарт API флагов (проект CNCF): код не привязан к поставщику (LaunchDarkly, Unleash, GrowthBook, собственный сервис). У мобильного приложения флаги — единственный способ выключить фичу без выпуска в магазине.

Вариант Б может поднять конверсию и уронить LCP. В эксперимент добавляют «ограничители» — Core Web Vitals и ошибки JavaScript — и останавливают вариант, если они ухудшились. Флаги после эксперимента удаляют из кода.

RUM (real user monitoring, мониторинг реальных пользователей) — сбор метрик прямо из браузеров покупателей: Core Web Vitals, ошибки, долгие задачи, с разбивкой по странице, устройству, сети и версии релиза. Библиотека web-vitals снимает LCP, INP и CLS так же, как Chrome.

    
лабораторный тест — это проверка нового автомобиля на испытательном треке. RUM — телеметрия с каждой проданной машины на настоящих дорогах, в снег и в пробках.

    

      
Отслеживание ошибок

глава 15 · аналитику доступность, языки и требования к фронтенду

    
Понедельник. Олег садится переписывать требования. В старой постановке было три строчки: «сайт должен быстро загружаться», «поддерживать все браузеры», «быть удобным». Ни одну нельзя проверить. Сначала — две темы, о которых часто забывают.

    
Доступность: WCAG 2.2

    
Доступность (accessibility, сокращают как a11y) — возможность пользоваться интерфейсом людям с особенностями зрения, слуха, моторики, внимания: через экранный диктор, только с клавиатуры, с увеличенным шрифтом. Стандарт — WCAG (Web Content Accessibility Guidelines) консорциума W3C; версия 2.2 — с октября 2023 года. Уровни A, AA, AAA; ориентир для требований — AA.

    
пандус у входа в магазин. Его делают для коляски, а пользуются им все: мама с детской коляской, курьер с тележкой, человек с чемоданом. Подписи к видео смотрят в метро без звука, а крупная кнопка удобна всем на ходу.

    

      
Что проверить в первую очередь
Всё работает с клавиатуры, фокус виден и не прячется под липкой шапкой. У картинок — осмысленный альтернативный текст. У полей — подписи, а ошибки объяснены словами, не только красным цветом. Контраст текста — не меньше 4,5:1 (крупного — 3:1). Кнопки и иконки — понятные диктору названия.

      
Что нового в 2.2
Цель нажатия — не меньше 24×24 CSS-пикселя. Фокус не должен скрываться под другими элементами. Вход без «когнитивных тестов» вроде распознавания картинок — должна быть альтернатива (например, вставка пароля из менеджера). Перетаскивание — с альтернативой нажатием. Помощь — в одном и том же месте на всех страницах. Не просить вводить одно и то же дважды.

    

    
Это не только этика. В ЕС с 28 июня 2025 года действует Европейский акт о доступности (EAA) для интернет-магазинов и многих других сервисов; техническая опора — стандарт EN 301 549, который ссылается на WCAG уровня AA. В России есть ГОСТ Р 52872-2019 с требованиями доступности интернет-ресурсов. Встроенная в дизайн-систему доступность (глава 10) — самый дешёвый способ её получить: каждая команда берёт уже доступную кнопку.
