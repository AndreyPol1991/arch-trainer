Это всё ещё один кусок, но внутри у него настоящие стены. У каждого модуля свои таблицы. Наружу торчит только витрина. А если кто-то полез в чужое — сборка падает, и правку просто не примут. Лучший старт для команды, которой рано в микросервисы, и лучшая подготовка к ним, если время придёт.

с самого начала чем он отличается от обычного монолита

Коротко: всеми тремя признаками монолита он остаётся. Одна сборка, один запуск, одна база. Меняется только одно — что происходит внутри.

🏢 Обычный монолит = опенспейс

Все сидят в одном зале без перегородок. Можно повернуться и взять бумагу с любого чужого стола. Быстро и удобно — ровно до того момента, когда людей стало тридцать и никто не помнит, чья это бумага и можно ли её трогать.

🚪 Модульный монолит = офис с кабинетами

То же здание, тот же этаж, все рядом. Но у каждого отдела свой кабинет с дверью. Нужен документ — стучитесь и просите через сотрудника, а не роетесь в чужих ящиках. Занимает на минуту дольше, зато через год понятно, у кого что.

Главная мысль. Разница не в том, что код лежит в других папках. Разница в том, что появилось правило, и его нельзя нарушить незаметно. Папки можно перекладывать как угодно — если нет проверки, через полгода все ходят ко всем.

три слова фасад, граф и цикл — что это вообще такое

Дальше в этом разделе встретятся три слова, без которых ничего не понятно. Разберём их сразу, по одному.

правила четыре правила, которые делают монолит модульным

Всё остальное — детали. Если выполняются эти четыре, вынести модуль в отдельный сервис позже — это вопрос недели: заменить вызов метода на HTTP-клиент за тем же интерфейсом.

принцип по какому правилу вообще раскладывать код

Один и тот же код можно разложить по папкам двумя способами. Файлы те же самые — разная только группировка. Нажмите на задачу и посмотрите, какие файлы придётся открыть.

Правило, из которого всё следует. Вместе надо класть то, что меняется вместе. Задачи приходят не «поменяйте все контроллеры», а «поменяйте что-то в заказах». Значит, и группировать надо по заказам, а не по контроллерам.

алгоритм как разложить свою систему: шесть шагов

Работает и для нового проекта, и для наведения порядка в существующем. Делайте по порядку, шаги опираются друг на друга.

Самая частая ошибка на шаге 2. Взять за основу таблицы базы данных. Таблицы — это следствие, а не причина. Начинать надо с того, что система делает, а не с того, что она хранит: от действий к данным, а не наоборот.

структура по слоям или по фичам

Одни и те же классы можно разложить двумя способами. Слева — привычная нарезка по техническим слоям, справа — по бизнес-возможностям. Разница не косметическая: во втором случае у модуля есть граница, и её можно защитить.

Package by layer — границы нет

// «Заказы» размазаны по четырём пакетам.
// Чтобы вынести заказы, надо собрать их по всей базе кода.

// Ничто не мешает написать:
class OrderService {
  private final PaymentRepo paymentRepo;  // чужой репозиторий
  void pay(Long id){
    paymentRepo.insertDirect(...);        // мимо чужой логики
  }
}

Package by feature — граница есть

// Модуль целиком в одном пакете. Наружу торчит
// только api/, всё остальное — internal/.
com.shop
├── order/
│     api/      OrderFacade, OrderDto, OrderPlaced
│     internal/ OrderService, OrderRepo, Order
├── payment/
│     api/      PaymentFacade, PaymentDto
│     internal/ PaymentService, PaymentRepo
└── catalog/
      api/      CatalogFacade, ProductDto
      internal/ ...

// Единственный законный способ:
class OrderService {
  private final PaymentFacade payments;   // контракт
  void pay(Long id){
    payments.charge(new ChargeCmd(id, sum)); // его правила
  }
}
Почему это работает как трамплин: в правой схеме PaymentFacade — это интерфейс. Когда придёт время вынести платежи в сервис, вы пишете вторую реализацию этого интерфейса поверх HTTP-клиента и подменяете бин. Вызывающий код не меняется вообще. В левой схеме такой точки подмены не существует, и выделение превращается в археологические раскопки.

диаграмма как модули разговаривают: посмотрите своими глазами

Клиент оплатил заказ. Модуль «Платежи» должен сообщить об этом модулю «Заказы». Три способа сделать это внутри одного процесса — выберите и прожмите шаги.

Обратите внимание на рамку транзакции на схеме. Всё, что внутри неё, база откатит целиком при любой ошибке. Всё, что снаружи, — уже нет. Именно расположение этой рамки и отличает три способа друг от друга, а вовсе не «синхронно или асинхронно».

механика как модули разговаривают внутри одного процесса

Три способа, от самого связного к самому развязанному. Выбор тот же, что между сервисами, — просто здесь он дешевле и обратим.

1. Синхронный вызов фасада

payments.charge(cmd). Просто, в одной транзакции, результат сразу. Но модули связаны: «Заказы» знают о существовании «Платежей» и падают вместе с ними.

Когда: нужен ответ прямо сейчас и в той же транзакции. Списание, резерв, проверка лимита.

2. Внутреннее доменное событие

events.publish(new OrderPlaced(id)). Издатель не знает подписчиков. Spring: @TransactionalEventListener(AFTER_COMMIT) — обработка после фиксации транзакции.

Когда: «случился факт, пусть заинтересованные реагируют». Уведомления, бонусы, аналитика.

3. Событие через очередь

То же событие, но уходит в брокер и обрабатывается отдельным потоком или процессом. Внутри монолита это уже репетиция распределённой системы.

Когда: обработка долгая, её не должно быть видно в ответе, и её надо уметь повторить при сбое.

Ловушка, на которой спотыкаются все: обычный @EventListener в Spring выполняется синхронно и в той же транзакции. Исключение у подписчика откатит транзакцию издателя — то есть «отправка письма не удалась» отменит заказ. Поэтому для реакций на свершившийся факт берут AFTER_COMMIT, а если реакция обязана выполниться — её кладут в ту же транзакцию через outbox.
