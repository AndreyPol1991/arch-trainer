Переписать всё с нуля почти всегда проваливается. Причина простая: пока вы переписываете, старая система продолжает меняться. Вы догоняете убегающую цель и два года ничего не выпускаете. Работает другой путь — менять по кускам, каждый раз выкатывая результат.

зачем это зачем трогать легаси

почему четыре причины провала «большого переписывания»

интерактив душитель (Strangler Fig) по шагам

Фикус-душитель обвивает дерево, постепенно заменяя его собой; когда дерево умирает, фикус стоит сам. Так же заменяют легаси: новое растёт снаружи, трафик переключается по кускам, старое отмирает. Пройдите по шагам.

приём ветвление по абстракции (branch by abstraction)

Когда заменяемый кусок находится внутри кода, а не за сетевой границей, душитель не работает — маршрутизировать нечем. Тогда точку переключения создают в самом коде.

// Шаг 1. Ввести абстракцию над существующей реализацией.
// Пока ничего не меняется — только появляется шов.
interface PricingEngine {
  Money priceOf(Order order);
}

class LegacyPricingEngine implements PricingEngine { /* тот самый код 2013 года */ }

// Шаг 2. Весь вызывающий код переводится на интерфейс. Выкатывается.
//        Поведение системы не изменилось ни на йоту — это важно:
//        рискованный шаг сделан отдельно от изменения логики.

// Шаг 3. Пишется новая реализация. Она не используется.
class NewPricingEngine implements PricingEngine { /* новая, с тестами */ }

// Шаг 4. Переключатель с процентом и сравнением результатов.
class SwitchingPricingEngine implements PricingEngine {
  public Money priceOf(Order o){
    Money legacy = legacyEngine.priceOf(o);
    if(flags.enabled("new-pricing", o.customerId())){
      Money fresh = newEngine.priceOf(o);
      if(!fresh.equals(legacy)) metrics.mismatch(o.id(), legacy, fresh); // расхождения видны
      return fresh;
    }
    return legacy;
  }
}

// Шаг 5. Процент растёт, расхождения разбираются.
// Шаг 6. Старая реализация и переключатель удаляются. Остаётся интерфейс.
Ключевое свойство: главная ветка всегда рабочая и всегда выкатываема. Никаких веток на три месяца, никакого «большого слияния», которое разбирают неделю. Каждый шаг — маленький, обратимый и выкатывается отдельно.

проверка параллельный прогон: как убедиться, что новое считает так же

Новая реализация получает тот же вход, что и старая; результаты сравниваются, наружу отдаётся старый. Расхождения логируются и разбираются до переключения.

Что это даёт

  • Проверка на настоящих данных, а не на придуманных тестовых.
  • Обнаруживаются случаи, о которых никто не помнил, — а в легаси их всегда десятки.
  • Нулевой риск: наружу идёт проверенный результат.
  • Появляется объективный критерий готовности: «расхождений меньше 0,01 % за неделю».

О чём забывают

  • Побочные эффекты новой реализации надо отключить: она не должна писать в базу, слать письма и дёргать партнёров.
  • Двойная нагрузка — прогон стоит ресурсов.
  • Расхождение не всегда означает ошибку в новом: часто обнаруживается баг в старом, который бизнес считает фичей.
  • Нужен человек, который будет разбирать расхождения, иначе их просто перестанут смотреть.

швы где резать легаси, если внутри всё связано

Шов — место, где поведение можно изменить, не правя код вокруг. Найти швы в коде без тестов и без границ — главная работа при подходе к легаси.

тесты как начать, если тестов нет вообще

1
Не писать «правильные» тесты — писать характеризующие.Характеризующий тест фиксирует текущее поведение, включая баги: «на такой вход система отвечает вот так». Цель не «проверить правильность», а «заметить изменение». Правильность здесь вторична: если поведение кривое, но от него зависят пользователи, менять его нельзя, не спросив бизнес.
2
Начинать с самых широких — через API или через UI.Модульные тесты требуют разрезать код, а его пока нельзя трогать. Тесты через внешнюю границу не требуют менять ничего и сразу дают страховку для рефакторинга внутри.
3
Применить approval-тесты для сложного вывода.Вместо ста утверждений — сравнение целого результата (JSON, отчёт, документ) с зафиксированным эталоном. Написать такой тест — минуты, а покрывает он всё сразу. При изменении эталон обновляется осознанно.
4
Покрывать не всё подряд, а то, что собираетесь менять.Попытка «сначала покрыть весь монолит тестами» умирает на третьем месяце. Покрывается только участок перед его правкой — и так постепенно.
5
Взять метрику покрытия изменённого кода, а не общего.Общее покрытие на легаси обречено расти медленно и демотивирует. Покрытие нового и изменённого кода можно требовать высоким с первого дня — и оно постепенно вытянет систему.
